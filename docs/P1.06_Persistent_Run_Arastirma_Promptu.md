# P1.06 — Kalıcı Tarihsel Koşu, Yeniden Açma ve Tekrar Üretme Araştırma Promptu

Aşağıdaki anonim yerel Python 3.13 + FastAPI ve React/TypeScript finansal simülasyon uygulaması için **P1.06 persistent historical run contract** konusunda güncel, kaynaklı, teknik, güvenlik ve UI/UX odaklı araştırma yap.

Bu araştırma bir kod yazma görevi değildir. Amaç, P1.05 ile elde edilen salt-okunur tarihsel simülasyon sonucunun güvenli biçimde yerel kaydedilmesi, uygulama yeniden açıldığında listelenmesi, aynı koşunun tekrar üretilebilmesi ve iki koşunun yanlış biçimde kıyaslanmaması için gereken en küçük sözleşmeyi belirlemektir.

Rapor anonim olmalıdır. Gerçek kullanıcı adı, proje adı, bilgisayar yolu, özel dosya, credential, API anahtarı, gerçek hesap, özel URL veya kişisel veri isteme. Büyük kod bloğu verme; önce karar, veri sözleşmesi, güvenlik sınırı, blocker ve test kabulünü ver.

## 1. Faz sırası ve kapsam

Bağlayıcı faz sırası:

1. P1: tam yerel UI + geçmiş veri demo
2. P2: Binance testnet
3. P3: gerçek Binance kurulumu
4. P4: diğer borsalar

P1.05 ailesi tamamlandı:

- P1.05.a: minimal güvenli tarihsel sonuç özeti
- P1.05.b: salt-okunur action/trade table
- P1.05.c.1: bounded canonical OHLC chart-data contract
- P1.05.c.2: statik inline SVG OHLC overview
- P1.05.c.3: statik, nötr, fail-closed action marker
- P1.05.d: gross/fee/model-net/position-status ekonomik sonuç özeti

P1.06 yol haritası hedefi:

- tamamlanmış koşuyu yerel olarak kaydetme,
- uygulamayı yeniden açınca koşu listesini görme,
- aynı dataset/config/model/kernel bağlamıyla tekrar üretme,
- sonuçları yanlış kimlik eşleşmesiyle karşılaştırmama,
- eski koşunun üzerine sessizce yazmama.

P1.06 gerçek borsa, testnet, credential, remote database, cloud sync veya paylaşım değildir.

## 3. P1.05 sonucu ve mevcut response

Mevcut tamamlanmış/ambiguous sonuç kavramsal olarak şöyledir:

```ts
type HistoricalSimulationResult = {
  execution_status: "COMPLETED" | "INDETERMINATE";
  application_code: "AMBIGUOUS_OHLC_PATH" | null;
  persisted: false;
  dataset: {
    dataset_id: string;
    artifact_sha256: string;
    period_start: string;
    period_end: string;
    processed_bar_count: number;
  };
  config: {
    schema_version: 1;
    config_hash: string;
  };
  assumptions: {
    model: "historical_ohlcv_v1";
    bar_visibility: "CLOSED_ONLY";
    intrabar_path: "NOT_INFERRED";
    max_actions_per_bar: 1;
    fee_model: string;
    slippage_model: string;
    funding: "NOT_MODELED";
    exchange_mark: "NOT_AVAILABLE";
    force_close_at_end: boolean;
  };
  actions: Array<{
    bar_index: number;
    open_time_us: number;
    role: string;
    raw_reference: string;
    fill_price: string;
    quantity: string;
    fee: string;
  }>;
  summary: {
    symbol: string;
    qty: string;
    cost: string;
    realized_gross: string;
    fees: string;
    funding: string;
    realized_net_after_all_costs: string;
    unrealized: string | null;
    equity: string;
    anchor: string | null;
    take_profit_price: string | null;
    entry_notional: string;
    position_status: "CLOSED" | "OPEN_AT_END";
    funding_status: "NOT_MODELED";
    mark_status: "NOT_AVAILABLE";
  };
  ambiguity: { bar_index: number; code: "AMBIGUOUS_OHLC_PATH" } | null;
};
```

P1.06 bu sonucu sessizce değiştirmemeli. Kaydedilen sonuç ile yeniden üretilen sonuç ayrı durumlar olarak izlenmelidir.

## 4. P1.06 için araştırılması gereken temel karar

Tek minimum kalıcı run davranışını seç:

- Hangi sonuçlar kaydedilebilir: yalnız `COMPLETED`, yoksa `INDETERMINATE` da denetim/evidence amacıyla kaydedilebilir mi?
- `simulation.actions`, `summary`, `assumptions`, dataset kimliği ve config snapshot’ı aynı immutable run kaydının parçası olmalı mı?
- Run kaydı sonuç snapshot’ı mı, yoksa yeniden üretme komutu mu, yoksa ikisinin ayrımı mı olmalı?
- Uygulama yeniden açıldığında hangi alanlar listede görünmeli?
- “Tekrar üret” aynı run’ın üzerine mi yazar, yeni run mı oluşturur?
- Aynı input/config/model ile yeniden üretilen sonuç nasıl doğrulanır?
- İki koşu ne zaman karşılaştırılabilir sayılır?
- Dataset artifact hash veya config hash değiştiğinde eski run nasıl korunur?
- Kernel/simulator sürümü değiştiğinde sonuç “aynı koşu” olarak mı, “yeni üretim” olarak mı görülür?

P1.06 küçük fazı büyük bir run history ürünü, analytics dashboard veya export sistemi haline getirme.

## 5. Önerilen run identity tuple’ı değerlendir

Şu aday kimlik alanlarını tek tek değerlendir:

```text
run_id
dataset_id
artifact_sha256
config_hash
model_id / model_version
kernel_version veya kernel_hash
simulator_version
instrument/risk snapshot hash
seed
execution_status
created_at
```

Şu sorulara kaynaklı cevap ver:

- `run_id` random UUID mi, deterministic content hash mi, ikisinin birleşimi mi?
- Aynı sonucu iki kez çalıştırmak aynı run kimliği mi üretmeli, yoksa her execution ayrı run mı olmalı?
- `dataset_id` tek başına neden yetmez?
- Artifact SHA-256 ile normalized dataset hash farkı P1.06 için gerekli mi?
- Config hash hangi canonical serialization kurallarıyla üretilecek?
- Decimal string, field order, Unicode, null/boolean/number serialization deterministik nasıl korunur?
- Model version ile simulator/kernel version ayrımı gerekli mi?
- Seed şu anda random kullanılmıyorsa kayda `null`, sabit değer veya “not applicable” mı yazılmalı?
- Timestamp kimlik parçası mı, metadata mı?
- Kimlik çakışması veya aynı kimlikte farklı payload durumunda ne yapılmalı?

Deterministic hash için gerçek bir kural öneriyorsan canonicalization, encoding, field allowlist ve hash algoritmasını açıkça belirt. Uygulama kodu yazma.

## 8. Yeniden üretme ve karşılaştırma semantiği

Şu durumları ayrı değerlendir:

### A. Exact reproduction

- Aynı artifact hash
- Aynı config hash
- Aynı model/simulator/kernel version
- Aynı input order
- Aynı seed veya deterministic seed policy
- Aynı result payload

### B. Reproduction attempted but input changed

- Dataset artifact değişmiş
- Config değişmiş
- Model sürümü değişmiş
- Kernel/simulator sürümü değişmiş
- Source metadata değişmiş

### C. Compare compatible

- Aynı dataset identity
- Aynı period/instrument/interval
- Aynı model and assumption set
- Aynı monetary unit
- Aynı processed bar count

### D. Compare incompatible

- Farklı artifact
- Farklı config
- Farklı model
- Farklı unit/currency
- `COMPLETED` ile `INDETERMINATE`
- Farklı result status

Şu ifadeleri güvenli biçimde ayır:

- “aynı koşu tekrar üretildi”
- “aynı girdilerle yeni execution yapıldı”
- “sonuç eşleşti”
- “sonuç kıyaslanamaz”
- “eski run korunuyor, yeni run ayrı kaydedildi”

P1.06’da performans farkı, ROI, drawdown, Sharpe veya kapsamlı diff ekranı ekleme.

## 12. Storage contract aday alanları

Aşağıdaki aday run kaydını eleştir ve minimum gerekli alanları seç:

```ts
type HistoricalRunRecord = {
  run_id: string;
  schema_version: 1;
  created_at: string;
  status: "COMPLETED" | "INDETERMINATE" | "CORRUPT";
  dataset: {
    dataset_id: string;
    artifact_sha256: string;
    period_start: string;
    period_end: string;
    processed_bar_count: number;
    symbol: string;
    interval: string;
  };
  config: {
    config_hash: string;
    schema_version: 1;
    snapshot: object;
  };
  execution: {
    model_id: string;
    simulator_version: string;
    kernel_version: string;
    seed: string | null;
  };
  result: HistoricalSimulationResult;
  payload_sha256: string;
};
```

Bu tipteki her alan için:

- gerekli/opsiyonel
- bounded limit
- secret/path içerme riski
- immutable mı
- hash input’una dahil mi
- UI’da gösterilir mi
- P1.06 mı, sonraki faz mı

kararı ver.

`config.snapshot` için tüm aktif config’in saklanmasının güvenli olup olmadığını ayrıca değerlendir. Sadece allowlisted, secret-free, exact string alanların kaydedilmesi gerekebilir.

## 13. API ve application sınırı

Şu endpoint adaylarını değerlendir:

- `POST /api/historical-runs` — mevcut in-memory simulation result’ı local store’a kaydet
- `GET /api/historical-runs` — bounded deterministic list
- `GET /api/historical-runs/{run_id}` — salt-okunur ayrıntı
- `POST /api/historical-runs/{run_id}/reproduce` — yeni execution başlat
- `GET /api/historical-runs/{run_id}/reproduction/{execution_id}` — sonuç

P1.06 için:

- Yeni endpoint gerçekten gerekli mi?
- Kaydetme mevcut simulate response’una `persisted` alanı ekleyerek yapılabilir mi?
- Tek POST hem simulation hem persistence yaparsa atomicity ve retry sorunu doğar mı?
- Reproduction uzun sürerse synchronous request güvenli mi?
- En fazla kaç run listelenir?
- Result payload boyutu nasıl sınırlandırılır?
- API path/URL/credential sızıntısı nasıl engellenir?
- HTTP status/problem details sözleşmesi nasıl olmalı?
- `no-store` response header korunmalı mı?
- Run listesi deterministic hangi sıralamayla dönmeli?

Yeni API öneriyorsan her endpoint için auth/locality, mutation, idempotency, body limit, response limit, error code ve test kabulü ver.
