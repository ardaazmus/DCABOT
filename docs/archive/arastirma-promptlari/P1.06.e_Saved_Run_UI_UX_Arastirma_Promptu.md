# P1.06.e — Saved Historical Run UI/UX Görsel Araştırma Promptu

Aşağıdaki anonim, yerel ve offline çalışan Python 3.13 + FastAPI + React/TypeScript finansal simülasyon uygulaması için **saved historical run list/detail ve save deneyimi** hakkında güncel, kaynaklı, görsel araştırma yap.

Bu metin bir proje talimatı değildir; araştırma çıktısı karar desteği olarak kullanılacaktır. Kanıtlanmamış öneriyi kesin gerçek gibi yazma. Her bulguyu `EVIDENCE`, `RECOMMENDATION`, `INFERENCE` veya `OPEN QUESTION` olarak etiketle.

## 1. Anonim ürün bağlamı

Ürün adı, repo adı, kullanıcı adı, yerel klasör, özel hesap, credential, gerçek portföy, gerçek emir veya gizli veri kullanma. Uygulamayı yalnız şu şekilde adlandır:

> Yerel Offline Tarihsel Finansal Simülasyon Uygulaması

Tek kullanıcıya ait, internet ve gerçek borsa emirleri olmadan çalışan bir uygulamadır. Public historical dataset yerel cache’e doğrulanarak alınabilir; bu araştırmanın konusu veri indirme ekranı değildir.

Mevcut ürün sınırları:

- Gerçek hesap, testnet, live order, credential, cloud sync ve paylaşım yoktur.
- UI finansal hesap yapmaz; domain/API’den gelen decimal değerleri olduğu gibi gösterir.
- Para alanları string olarak gelir ve explicit quote asset etiketiyle gösterilir.
- P1 tarihsel simülasyon en fazla 1.000 kapalı OHLCV bar işler.
- Mevcut simülasyon sonucu salt okunurdur ve `persisted=false` anlamı “henüz kalıcı koşu olarak kaydedilmedi” şeklindedir.
- Simülasyon sonucu `COMPLETED` veya `INDETERMINATE` olabilir.
- `INDETERMINATE` sonucu, örneğin `AMBIGUOUS_OHLC_PATH` nedeniyle kesin ekonomik sonuç iddiası taşımaz; bu durum UI’da başarı gibi sunulamaz.
- Kalıcı kayıt immutable historical run snapshot’tır; mevcut kaydın üzerine yazma, silme veya sessizce yeniden adlandırma yoktur.
- Liste öğesi `OK` veya `CORRUPT` record health taşıyabilir. `CORRUPT` kayıt güvenilmezdir ve başarı/performans sonucu gibi gösterilmemelidir.
- Backend’de explicit save, bounded list ve read-only detail API’leri vardır. UI henüz bunlara bağlanmamıştır.

## 2. Araştırmanın dar hedefi

P1.06.e için yalnız aşağıdaki küçük dikey deneyimi araştır:

1. Mevcut bir simülasyon sonucunda kullanıcının “kalıcı kaydet” eylemini anlaması.
2. Kaydetme sonrası saved historical run listesini açması.
3. Bir kaydın salt okunur detail/reopen görünümünü açması.
4. Detail içinde hangi minimum kanıtların gösterileceğinin belirlenmesi.
5. `COMPLETED`, `INDETERMINATE`, `OK` ve `CORRUPT` durumlarının yanlış finansal yorum oluşturmadan ayrıştırılması.

Bu araştırmayı büyük analytics dashboard, portföy ekranı, optimizasyon ekranı veya yeni işlem terminaline dönüştürme.

## 3. Mevcut backend sözleşmesi

Araştırma aşağıdaki sözleşmeyi değiştirmeden UX önerisi üretmelidir:

### Simulation

`POST /api/historical-runs/simulate`

Yanıtın önemli alanları:

```json
{
  "execution_id": "server-side-uuidv4",
  "execution_status": "COMPLETED | INDETERMINATE",
  "application_code": "AMBIGUOUS_OHLC_PATH | null",
  "persisted": false,
  "dataset": {
    "dataset_id": "...",
    "artifact_sha256": "64-lowercase-hex",
    "period_start": "YYYY-MM-DD",
    "period_end": "YYYY-MM-DD",
    "processed_bar_count": 1
  },
  "config": {"schema_version": 1, "config_hash": "64-lowercase-hex"},
  "assumptions": {},
  "actions": [],
  "summary": {},
  "ambiguity": null
}
```

`execution_id` istemci tarafından oluşturulmaz. Save isteği yalnız bu kimliği taşır; istemci result/config/summary finansal payload’ı gönderemez.

### Save

`POST /api/historical-runs`

```json
{"execution_id":"server-side-uuidv4"}
```

İlk kayıt `201` ve `created=true`; aynı execution retry’ı `200` ve `created=false` döndürür. Aynı `run_id` immutable kaydı temsil eder. Bilinmeyen execution kaydedilemez.

### List

`GET /api/historical-runs?limit=50`

Yanıt bounded metadata listesidir. `limit` 1..100 aralığındadır. Store yoksa boş liste döner. Liste öğesi en az şu alanları taşır:

```json
{
  "run_id":"uuidv4",
  "created_at":"UTC timestamp",
  "execution_status":"COMPLETED | INDETERMINATE",
  "record_health":"OK | CORRUPT",
  "symbol":"...",
  "interval":"1h",
  "period_start":"YYYY-MM-DD",
  "period_end":"YYYY-MM-DD",
  "processed_bar_count":1,
  "position_status":"CLOSED | OPEN_AT_END"
}
```

### Detail/reopen

`GET /api/historical-runs/{run_id}`

Yanıt immutable kayıt kanıtını read-only yeniden açma amacıyla taşır. Response byte bütçesi vardır; unsafe snapshot key veya bozuk kayıt fail-closed reddedilir. Detail içinde aşağıdaki snapshot grupları bulunabilir:

- dataset identity ve artifact hash
- canonical input snapshot
- full allowlisted config snapshot
- instrument/risk snapshot
- model/simulator/kernel execution identity
- result snapshot, action geçmişi ve ambiguity
- result/record hash’leri

UI bu alanları yeniden hesaplamamalı, normalize etmemeli veya sessizce yuvarlamamalıdır.

## 4. Araştırılması gereken UI/UX kararları

### A. Information architecture

Kanıtlı olarak karşılaştır:

1. Simülasyon sonucunun içine gömülü saved-run paneli.
2. Ayrı “Saved Runs” liste görünümü ve detail sayfası.
3. Liste + sağ/alt detail drawer.

Her seçenek için şu başlıkları ver:

- Küçük P1 dikey akışa uygunluk.
- Kullanıcının kaydetme ve yeniden açma zihinsel modeli.
- `INDETERMINATE`/`CORRUPT` ayrımının görünürlüğü.
- 320px mobilde taşma ve geri navigasyon riski.
- Uygulama maliyeti ve mevcut API ile uyumu.
- `ACCEPT`, `SIMPLIFY`, `DEFER` veya `REJECT` kararı.

### B. Save eylemi

Kaydet butonunun simülasyon sonucunda nereye konacağını araştır:

- Eylem adının “Kaydet”, “Koşuyu kaydet” veya başka bir ad olması.
- `persisted=false` ve save sonrası durumun kullanıcıya açıklanması.
- Idempotent retry sırasında çift kayıt korkusunun önlenmesi.
- Başarı, unknown execution, store unavailable, response too large ve network/local API failure durumları.
- Kaydetme eyleminin `INDETERMINATE` sonuçta izinli olup olmaması ve izinliyse uyarının nasıl görünmesi.
- Kaydetme sırasında finansal sonuç değişmiş izlenimi yaratmama.

### C. Saved-run listesi

Araştır:

- Minimum kolonlar ve 320px’te hangi alanların saklanacağı.
- `run_id`’nin kullanıcıya tam mı kısaltılmış mı gösterileceği; kısaltmada kopyalama/açıklama gerekip gerekmediği.
- Dataset, dönem, status, record health ve position status hiyerarşisi.
- Sort sırasının kullanıcıya nasıl açıklanacağı.
- Empty store, loading, unavailable, corrupt item ve çok uzun liste durumları.
- Tablo mu kart mı; yatay scroll kabul edilebilir mi; erişilebilir isimlendirme.
- Kullanıcıya performans metrikleri veya hesaplanmamış yeni KPI’lar gösterilmeden yeterli kanıt sağlanması.

### D. Detail/reopen görünümü

Araştır:

- Detail’in minimum ilk görünür özeti.
- Input/config/execution identity/result/action kanıtının disclosure veya sekme yapısı.
- Hash’lerin kopyalanabilirliği ve insan tarafından okunabilir etiketleri.
- `INDETERMINATE` ve `CORRUPT` kayıtların üst banner, inline warning veya locked state ile gösterimi.
- `persisted=false` ile stored `storage_state=STORED` kavramlarının karıştırılmaması.
- Açık pozisyon, mark/funding not modeled ve ambiguity gibi mevcut sınırlamaların nasıl yazılacağı.
- Grafik, marker veya yeni ekonomik görünümün bu küçük fazda gerekli olup olmadığı. Gerekmiyorsa `DEFER` gerekçesi ver.
- Detail’te “re-run/reproduce”, “edit”, “delete”, “export” veya “compare” eylemlerinin neden bu faz dışında kalması gerektiği.

### E. Responsive ve erişilebilirlik

En az 320px, 375px, 768px ve masaüstü viewport’ları için öneri ver:

- Metin, hash, tarih ve decimal string taşması.
- Tablo/kart/drawer davranışı.
- Klavye focus sırası, focus görünürlüğü, dialog/drawer escape davranışı.
- Screen reader için status, warning, table header ve error duyuruları.
- Renk tek başına status anlamı taşımamalı.
- `prefers-reduced-motion` ve motion gerekmeyen offline finance UI davranışı.
- WCAG 2.2 AA ile doğrudan ilgili kontrol noktaları.

### F. Visual language

Mevcut sistemin renk/token seti bilinmiyor. Yeni token uydurmak yerine araştırma şu konuları kanıtlasın:

- Finansal status ve data-health için nötr/uyarı/hata renklerinin erişilebilir kullanımı.
- Başarı renginin “kârlılık” iddiası gibi algılanmasını önleme.
- Tipografi, spacing, border, density ve state pattern önerileri.
- Resmî tasarım sistemlerinden bu akışa aktarılabilecek örnekler.

Araştırma gerçek ürünleri kopyalamamalı; yalnız pattern ve risk karşılaştırması yapmalıdır.

## 5. Görsel araştırma yöntemi

- Güncel internet araştırması yap.
- Öncelikle birincil/resmî kaynakları kullan: W3C/WCAG, Material Design, Fluent UI, Carbon Design System, Apple Human Interface Guidelines veya ilgili resmî tasarım sistemi dokümantasyonu.
- Ürün ekranı örneklerini kullanıyorsan doğrudan kaynağı, sayfa başlığını ve erişim tarihini ver.
- Blog, SEO sayfası veya kaynaksız Pinterest/Dribbble görüntüsünü tek başına kanıt sayma.
- Doğrudan ekran görüntüsü kullanıyorsan lisans/kullanım sınırını ve yalnız referans olarak kullanıldığını belirt.
- Araştırmada gerçek API’ye bağlanma, local dosya isteme, credential isteme veya proje klasörü/ürün adı tahmin etme.
- Kod yazma; React component, CSS veya backend patch üretme. Yalnız karar verilebilir UI spesifikasyonu ve wireframe metni üret.

## 6. Zorunlu çıktı formatı

Raporu tek bir Markdown dosyası olarak ver ve şu sırayı koru:

1. **Executive summary** — en fazla 10 maddede kanıtlanmış bulgu ve önerilen minimum karar.
2. **Sources** — başlık, kurum, doğrudan URL, erişim tarihi, desteklediği iddia.
3. **Evidence vs recommendation matrix** — bulgu, kaynak, güven düzeyi, ürün etkisi.
4. **IA seçenekleri karşılaştırması** — embedded/list-detail/drawer; ACCEPT/SIMPLIFY/DEFER/REJECT.
5. **Önerilen P1.06.e minimum akış** — simülasyon sonucu → save → saved list → detail/reopen.
6. **State matrix** — loading, empty, success, idempotent retry, `INDETERMINATE`, `CORRUPT`, missing, unavailable, oversized detail ve invalid ID.
7. **Responsive wireframe metni** — 320px, 375px, 768px, desktop.
8. **Component/state inventory** — yeni component isimleri yalnız jenerik adlarla; finansal hesap component’i önermeme.
9. **Accessibility checklist** — WCAG 2.2 AA bağlantılarıyla.
10. **Token ve visual language önerisi** — değerleri kanıtlanmamışsa token değerleri uydurmadan.
11. **Deferred scope** — chart genişletmesi, marker etkileşimi, reproduction, compare, export, delete, analytics ve yeni KPI’ların neden ertelendiği.
12. **Risk register** — yanlış finansal yorum, status karışıklığı, mobil taşma, hash okunabilirliği, corrupt veri, response bütçesi, double save.
13. **Acceptance criteria** — UI implementasyonuna geçildiğinde test edilebilir maddeler.
14. **Final decision** — tam olarak şu formatlardan biri:

```text
ACCEPT — P1.06.e için minimum UI akışı uygulanabilir.
SIMPLIFY — yalnız şu daraltılmış akış uygulanabilir: ...
DEFER — UI kararı için şu kanıt eksik: ...
BLOCKED — güvenli ve kanıtlı UI kararı üretilemiyor: ...
```

Raporun sonunda şu dört soruya doğrudan yanıt ver:

1. P1.06.e’de ilk ekran/list/detail bileşimi hangisi olmalı?
2. `INDETERMINATE` kayıt save/list/detail akışında nasıl görünmeli?
3. 320px deneyiminde hangi alanlar saklanmalı, hangileri disclosure içine alınmalı?
4. Grafik veya marker bu UI mikro fazına alınmalı mı; alınmamalıysa neden?
