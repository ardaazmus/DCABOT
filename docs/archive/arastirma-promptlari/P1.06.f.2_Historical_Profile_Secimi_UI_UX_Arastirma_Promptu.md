# Anonim UI/UX Araştırma Promptu — Historical Profile Seçimi

## Görev

Yerel, offline-first bir finansal simülasyon uygulamasında verified tarihsel dataset ile çalışacak explicit `historical profile` seçiminin en küçük, güvenli ve anlaşılır UI/UX çözümünü araştır.

Bu araştırma gerçek emir, testnet, hesap bağlama, yatırım tavsiyesi veya performans iddiası için değildir. Amaç yalnızca kullanıcının hangi immutable offline config profiliyle hangi verified dataset’i çalıştıracağını açıkça görmesi ve yanlış/örtük seçimlerin engellenmesidir.

## Anonim uygulama bağlamı

Uygulama yerel Python 3.13 + FastAPI backend ve React/TypeScript frontend’den oluşan offline bir historical simulation ürünüdür. Şu an mevcut ekranda:

- Verified public kline dataset kataloğu ve dataset detay paneli vardır.
- Preflight kartı dataset sembolü, interval, tarih aralığı, bar sayısı, timestamp standardı ve artifact SHA-256 özeti gösterir.
- Run-plan kartı aktif offline config snapshot’ını ve deterministic config hash’ini gösterir.
- Kullanıcı onayından sonra yalnız `historical_ohlcv_v1` simulated run çalışır.
- Sonuçta minimal read-only sonuç, action table, statik OHLC görünümü ve fail-closed action marker bulunur.
- Save sonrası ayrı Saved Runs list/detail görünümü vardır.
- Frontend finansal hesap yapmaz; para/miktar değerlerini string olarak gösterir.
- Gerçek emir, testnet/live venue, credential, re-run, edit, delete, compare veya export yoktur.

Backend’te iki explicit immutable profile bulunmaktadır:

1. `paper`
2. `historical_demo_btcusdt_1h_v1`

Historical demo profile’ın güvenlik/kanıt alanları:

- `profile_id`: `historical_demo_btcusdt_1h_v1`
- `profile_version`: `1`
- `venue_filter_provenance`: `project_fixture`
- `historical_filter_claim`: `false`
- `anchor_source`: `dataset_first_bar_open`
- profile yalnız belirli verified BTCUSDT/1h dataset’iyle eşleşir.

Kullanıcıya “Binance’in o tarihli venue filtreleri kesin olarak buydu” denmemelidir. `project_fixture`, yalnız uygulamanın offline demo uyumluluk fixture’ı anlamına gelir. Profile seçimi explicit olmalı; dataset’e bakıp quantity, anchor veya config değerlerini sessizce değiştirmek yasaktır.

## Araştırma sorusu

Mevcut dataset katalog/preflight/run-plan ekranına, kullanıcıyı yanlış profile seçimine teşvik etmeden explicit historical profile seçimini nasıl eklemek gerekir?

Amaç yeni bir dashboard veya kapsamlı finansal ekran tasarlamak değildir. En küçük mevcut arayüz değişikliği araştırılmalıdır.

## İncelenecek kararlar

### 1. Kontrol tipi ve yerleşim

Aşağıdaki seçenekleri karşılaştır:

- Preflight kartı içinde native `select`/combobox
- Run-plan kartı içinde profile satırı + “Değiştir” eylemi
- Dataset detay panelinde profile seçimi
- Ayrı küçük “Historical execution profile” kartı
- Profile seçim ekranı/step’i

Mevcut ekranın bilgi mimarisini bozmadan, dataset ile profile pairing’ini en açık gösteren seçeneği öner. Neden daha büyük bir ekran veya modal gerekmediğini de belirt.

### 2. Varsayılan davranış

Şunları ayrı ayrı değerlendir:

- İlk açılışta `paper` seçili görünmesi
- Verified BTCUSDT/1h dataset seçildiğinde `historical_demo_btcusdt_1h_v1` otomatik seçilmesi
- Hiçbir profile seçmeden run başlatmanın engellenmesi
- Backend’in sessiz default profile seçmesi

Özellikle “dataset görüldü, profile otomatik değişti” davranışının reproducibility ve finansal yanlış yorum riskini değerlendir. Tavsiye edilen davranış explicit ve fail-closed olmalı; otomatik eşleşme varsa bunun yalnız öneri olarak gösterilip kullanıcı onayı gerekip gerekmediğini açıkla.

### 3. Kullanıcıya gösterilecek minimal bilgiler

Profile option/card için minimum alanları belirle:

- profile ID veya insan okunur etiket
- profile version
- eşleşen dataset/symbol/interval
- venue filter provenance
- historical filter claim durumu
- anchor source
- config hash
- base/safety/safety count/max cap gibi config snapshot değerleri

Hangi bilgilerin seçim öncesi, hangilerinin seçim sonrası gösterilmesi gerektiğini ayır. Hash’in kısaltılmış gösteriminde kopyalama veya disclosure gerekir mi değerlendir.

### 4. Uyarı ve yanlış yorumlama

`project_fixture` ve `historical_filter_claim=false` için kısa, Türkçe, nötr ve alarm yorgunluğu yaratmayan bir uyarı metni öner. Aşağıdaki anlam korunmalı:

> Bu profile offline demo uyumluluk fixture’ıdır; ilgili tarih için venue filtrelerinin tarihsel olarak doğrulandığını göstermez.

Uyarının hangi seviyede olması gerektiğini karşılaştır:

- inline note
- warning callout
- confirmation dialog
- disabled run control yanında açıklama

`paper` ile `historical_demo` arasındaki farkın kullanıcı tarafından yanlışlıkla gerçek venue uyumluluğu sanılmasını önle.

### 5. 320px mobil davranış

320px genişlikte şu öğelerin taşmadan okunabilir kalması için somut öneri ver:

- profile select
- uzun profile ID
- provenance etiketi
- warning metni
- config hash
- dataset/profile mismatch hatası

Native select, stacked card, disclosure/details, wrap/break davranışlarını karşılaştır. Yatay sayfa scroll’u oluşmamalı. Uzun hash/path/URL gösterme; path ve URL zaten UI sözleşmesi dışıdır.

### 6. Durum makinesi

Şu durumların her biri için görünür UI davranışı ve run butonu durumu öner:

- profile loading
- profile list unavailable
- valid profile selected
- no profile selected
- selected profile does not match dataset
- config hash mismatch/stale plan
- `project_fixture` warning
- simulation completed
- simulation indeterminate
- save state (`persisted=false` result vs stored run)

Profile değiştiğinde preflight/run-plan/simulation/save state’in hangileri temizlenmeli veya yeniden yüklenmeli? Eski HTTP yanıtının yeni seçimi ezmemesi için gerekli UI state kuralını yaz.

### 7. Erişilebilirlik

Keyboard, screen reader, focus order, label association, error announcement, warning semantics ve reduced-motion açısından minimum kabul kriterlerini ver. Profile seçimi confirmation gerektiriyorsa Escape/focus restore davranışını belirt.

### 8. Görsel referanslar

Güncel resmi veya güvenilir ürün dokümanlarından en az üç referans bul:

- explicit environment/profile/config selection
- dataset/config compatibility veya validation warning
- dar ekranda bounded settings/control presentation

Her referans için doğrudan URL, ürün/ekran adı, gözlenen somut UI kararı ve bu yerel offline uygulamaya aktarılabilecek kısmı yaz. Screenshot gerekiyorsa hangi bölgenin neden önemli olduğunu belirt. Marka/renk kopyalamak yerine bilgi mimarisi ve hata önleme kararlarını incele.

## Beklenen çıktı

Yanıtı aşağıdaki başlıklarla üret:

1. Kısa karar özeti
2. Seçenek karşılaştırma tablosu
3. Önerilen en küçük UI akışı
4. Exact profile selection contract önerisi
5. Warning/error metinleri (Türkçe)
6. 320px responsive kuralları
7. Accessibility kabul kriterleri
8. State transition tablosu
9. Doğrudan kaynaklar ve her kaynağın somut kanıtı
10. Uygulama kapsamı: ACCEPT / SIMPLIFY / DEFER / REJECT
11. UI uygulanmadan önce kontrol edilmesi gereken backend/API varsayımları
12. Test senaryoları ve beklenen sonuçlar

## Sıkı sınırlar

- Bu prompttaki anonim uygulama bağlamı dışında proje adı, yerel path, kullanıcı adı, makine bilgisi, secret, API key, credential, private endpoint veya gerçek hesap bilgisi isteme.
- Gerçek emir, testnet/live entegrasyonu, hesap/fee tier, kaldıraç, funding, liquidation, yatırım tavsiyesi veya kârlılık sonucu araştırma kapsamı dışıdır.
- Historical venue filter snapshot yoksa bunu doğrulanmış gerçek gibi sunma.
- `project_fixture` ile `historical_verified` ayrımını koru.
- Frontend finansal hesap, quantity/anchor normalization veya config mutation önermeme; bunlar backend sözleşmesi ve explicit profile ile sınırlı kalmalı.
- Büyük kod blokları verme. Gerekirse yalnız küçük, framework-neutral wireframe/DOM örneği ver.
- Her iddiayı doğrudan kaynakla destekle; kaynak yoksa `BİLİNMİYOR` veya `ÖNERİ` etiketi kullan.
- Sonunda hangi önerilerin kanıtla doğrulandığını, hangilerinin yalnız ürün/UI önerisi olduğunu açıkça ayır.
