# P1.17.b — Public read-only feed contract araştırma promptu

## Araştırma görevi

Yerel Windows uygulamasında kullanılacak public read-only piyasa verisi akışı için güncel, resmi kaynaklara dayalı ve uygulama kararını doğrudan destekleyen bir sözleşme araştırması hazırla.

Uygulama bağlamı:

- Python 3.13, Windows, offline-first yerel uygulama.
- Uygulama tarihsel OHLCV dosyasını doğrular ve offline simülasyon yapar.
- Public veri okunabilir; private credential, hesap bakiyesi, gerçek emir ve testnet bu araştırmanın dışında kalır.
- Canlı veri yalnız gözlem/paper-trading adayıdır; gerçek emir authority’si olamaz.
- Finansal değerler uygulamada `Decimal` dış sınırı ve exact domain arithmetic ile korunur; `float` ekonomik hesapta kullanılmaz.
- Araştırma anonim olmalıdır: repo adı, yerel yol, kullanıcı adı, API anahtarı, özel hesap, token veya gizli yapılandırma isteme.

## Zorunlu kapsam

### 1. Kaynak ve transport seçimi

En az iki güncel resmi public seçenek karşılaştır:

- Public REST polling.
- Public WebSocket/stream.
- Gerekliyse tarihsel public archive ile canlı akışın ayrımı.

Her seçenek için resmi dokümantasyon URL’si, son güncelleme/sürüm bilgisi, erişim tarihi, sembol/ürün kapsamı, payload örneği, timestamp birimi, event/receive/processing time alanları, rate limit, bağlantı limiti, authentication gerekip gerekmediği ve coğrafi/erişim kısıtı belirtilsin.

Birincil kaynak yoksa bunu `NOT_VERIFIED` yaz. Blog, forum, kod deposu veya genel backtest yazısını resmi protokol kuralı gibi kullanma.

### 2. Canonical read-only event contract

Aşağıdaki alanlar için kesin öneri ver veya veri yoksa `UNKNOWN/INDETERMINATE` kuralı tanımla:

- `source_id`, `transport`, `symbol`, `product`, `event_id` veya kaynak sequence.
- `event_time_us`, `receive_time_us`, `processing_time_us` ayrımı.
- price, quantity, bid/ask veya candle alanları; her birinin asset/unit anlamı.
- source sequence, duplicate, out-of-order ve reconnect sonrası tekrar davranışı.
- payload hash/canonical serialization ve result/run lineage ilişkisi.
- UTC/timezone ve timestamp normalization.

Tüm numeric alanlar için JSON number mı, decimal string mi, ölçekli integer mı kullanılacağını kaynak kanıtıyla ayır. “String kullan” tek başına yeterli değildir; parse, precision, range ve serialization kuralını yaz.

### 3. Stale, disconnect, reconnect ve gap politikası

Ölçülebilir ve fail-closed politika öner:

- Son geçerli gözlem zamanı ve stale eşiği.
- Heartbeat/ping/pong veya server event ile client receive zamanı ayrımı.
- Timeout, connection close, malformed payload, sequence gap, duplicate ve out-of-order event state’leri.
- Reconnect/backoff sınırı; reconnect sırasında gelen eski olayların kabul/red kuralı.
- Gap doldurma yapılacaksa hangi veriyle, hangi koşulda ve hangi durumda `INDETERMINATE`.
- Sistem saati yoksa veya güvenilir değilse hangi saat authority’sinin kullanılacağı.
- Uygulama kapanıp açıldığında in-memory stream state’in yeniden kurulup kurulamayacağı.

Borsanın resmi sözleşmesinde olmayan bir stale eşiğini borsa gerçeği gibi sunma. Eşik uygulama policy’si ise açıkça synthetic/application policy olarak etiketle.

### 4. Live data → simulated adapter sınırı

Public gözlemin simulated execution’a dönüşmesi için şu ayrımı kesinleştir:

- Observation event’in ekonomik fill olmadığı.
- Market/limit/stop emri gözleminin hangi koşulda yalnız candidate/trigger olduğu.
- Public ticker ile historical OHLCV’nin aynı authority sayılamayacağı.
- Spread, slippage, fee, latency, queue, volume participation ve intra-bar path eksikse hangi sonuçların üretilemeyeceği.
- `SIMULATED`, `READ_ONLY`, `NO_CREDENTIAL`, `NO_REAL_ORDER` işaretlerinin response ve persistence’ta nasıl taşınacağı.
- Canlı verinin geçmiş simülasyon sonucunu overwrite etmemesi.

### 5. Offline fallback ve güvenlik

- Network yokken mevcut verified historical artifact ile uygulamanın nasıl çalışmaya devam edeceği.
- Live feed başarısızken partial/stale observation’ın kullanılamaması.
- Public URL allowlist, redirect, TLS/host doğrulaması, response-size, decompression, cache publication ve retry sınırları.
- Secret/credential sızıntısı, URL/path disclosure, log redaction ve hata response güvenliği.
- Dosyaya veya SQLite’a kalıcı yazım varsa crash/recovery ve idempotency sınırı.

### 6. Test ve bağımsız oracle matrisi

Her karar için en az bir expected ve unexpected test tanımla:

- Aynı event duplicate → no-op.
- Aynı event identity, farklı payload → conflict/fail-closed.
- Out-of-order event.
- Sequence gap.
- Stale threshold boundary.
- Disconnect/reconnect.
- Malformed payload, wrong symbol, wrong product, wrong timestamp unit.
- Network failure with intact offline fallback.
- Public observation’ın ekonomik fill’e dönüşmemesi.
- Public feed sonucu ile historical run identity’nin ayrılması.

Mümkünse production reducer’ı kullanmayan küçük, bağımsız Python 3.13 stdlib oracle/pseudocode ver. Oracle’ın production kodunu kopyalamadığını ve hangi alanları yalnız kontrol ettiğini açıkla.

### 7. Karar matrisi

Sonuçları şu etiketlerle sınıflandır:

- `ACCEPT`: Resmi kaynak + yerel uygulanabilirlik + bağımsız test yeterli.
- `ACCEPT_WITH_LIMITATION`: Yalnız açıkça sınırlanmış read-only/simulated davranış.
- `DEFER`: Eksik karar veya calibration var; uygulama yapılmaz.
- `NO-GO`: Yanlış ekonomik/operasyonel iddia riski var.
- `NOT_VERIFIED`: Kaynak veya iddia doğrulanamadı.

Özellikle şu sorulara açık cevap ver:

1. P1 read-only canlı feed için REST mi WebSocket mi, yoksa ikisi ayrı kullanım mı?
2. Minimum güvenli event schema nedir?
3. Stale ve sequence gap hangi durumda feed’i `INDETERMINATE` yapar?
4. Reconnect sonrası duplicate/out-of-order event nasıl ele alınır?
5. Network yokken verified historical cache hangi koşulda authoritative fallback olur?
6. Live observation’ın simulated fill’e dönüşmesini hangi kesin sınırlar engeller?
7. Hangi davranışlar resmi kaynakla, hangileri yalnız uygulama policy’siyle belirlenebilir?

## Teslim formatı

Tek bir Markdown raporu teslim et ve şu bölümleri kullan:

1. Executive decision.
2. Scope and explicit non-goals.
3. Source/evidence register: URL, kurum, sürüm/last-updated, erişim tarihi, doğrudan desteklediği iddia.
4. Transport comparison.
5. Canonical event schema and units.
6. Time taxonomy.
7. Stale/gap/reconnect state machine.
8. Offline fallback and security boundary.
9. Observation-to-simulation boundary.
10. Independent test/oracle matrix with expected and unexpected states.
11. Conflict register and unresolved questions.
12. Implementation gate: `ACCEPT`, `ACCEPT_WITH_LIMITATION`, `DEFER`, `NO-GO`, `NOT_VERIFIED`.
13. Safe minimal interface/pseudocode only if it is necessary; network credential, private API veya gerçek emir kodu verme.

Her önemli iddianın hemen yanında doğrudan kaynak bağlantısı ve kanıt türü olsun. Kaynaklar çelişirse hangi resmi kaynağın neden üstün tutulduğunu yaz. Kaynakta bulunmayan timeout, stale eşiği, reconnect veya fill sonucunu gerçek borsa davranışı gibi uydurma.
