# P1.05.c — Grafik Veri Sözleşmesi ve Action Marker Araştırma Promptu

Aşağıdaki anonim yerel Python 3.13 + React/TypeScript finansal simülasyon uygulaması için P1.05.c fazında güvenli grafik veri sözleşmesi ve action marker mimarisi üzerine güncel, kaynaklı araştırma yap.

Bu çalışma yalnızca araştırma ve karar girdisidir; proje talimatı değildir. Proje adı, klasör yolu, kullanıcı adı, gerçek hash, hesap bilgisi, API anahtarı, credential, özel config veya gerçek kullanıcı verisi rapora girme.

## 1. Mevcut anonim sistem bağlamı

Uygulama:

- Windows üzerinde yerel çalışır.
- Python 3.13 + FastAPI backend kullanır.
- React + TypeScript frontend kullanır.
- Public tarihsel OHLCV dataset’i yerel cache’ten okur.
- Network emirleri, testnet, live hesap ve credential yolu henüz yoktur.
- Tarihsel simülasyon en fazla 1.000 kapalı bar işler.
- Simülasyon `historical_ohlcv_v1` modeliyle çalışır.
- Finansal hesaplar backend/domain katmanında yapılır.
- Frontend finansal PnL, fee, equity veya pozisyon hesabı yapamaz.
- Finansal decimal değerler backend’den string olarak gelir.
- Çekirdek ekonomik doğruluk kaynağı backend/domain katmanıdır.

Tamamlanan küçük fazlar:

- Preflight özeti
- Aktif config’e bağlı run-plan
- Bounded historical simulation
- Minimal güvenli sonuç özeti
- Read-only action/trade table

P1.05.b’de mevcut `actions` alanından şu davranış eklendi:

- `COMPLETED` sonuçlarda read-only action table
- Masaüstünde semantik tablo
- Mobilde responsive kart/liste görünümü
- `INDETERMINATE` sonuçlarda action table gösterilmiyor
- `OPEN_AT_END` durumunda sahte kapanış aksiyonu eklenmiyor
- Frontend finansal hesap yapmıyor
- `raw_reference` varsayılan tabloda gösterilmiyor

## 2. Mevcut simülasyon response özeti

Mevcut response yaklaşık olarak şu alanları içerir:

```typescript
type HistoricalSimulationResult = {
  execution_status: "COMPLETED" | "INDETERMINATE";
  application_code: "AMBIGUOUS_OHLC_PATH" | null;
  persisted: false;

  dataset: {
    dataset_id: string;
    artifact_sha256: string;
    period_start: string;
    period_end: string;
    processed_bar_count: number;
  };

  config: {
    schema_version: 1;
    config_hash: string;
  };

  assumptions: {
    model: "historical_ohlcv_v1";
    bar_visibility: "CLOSED_ONLY";
    intrabar_path: "NOT_INFERRED";
    max_actions_per_bar: 1;
    fee_model: string;
    slippage_model: string;
    funding: "NOT_MODELED";
    exchange_mark: "NOT_AVAILABLE";
    force_close_at_end: boolean;
  };

  actions: Array<{
    bar_index: number;
    open_time_us: number;
    role: string;
    raw_reference: string;
    fill_price: string;
    quantity: string;
    fee: string;
  }>;

  summary: {
    symbol: string;
    qty: string;
    cost: string;
    realized_gross: string;
    fees: string;
    funding: string;
    realized_net_after_all_costs: string;
    unrealized: string | null;
    equity: string;
    anchor: string | null;
    take_profit_price: string | null;
    entry_notional: string;
    position_status: "CLOSED" | "OPEN_AT_END";
    funding_status: "NOT_MODELED";
    mark_status: "NOT_AVAILABLE";
  };

  ambiguity: {
    bar_index: number;
    code: "AMBIGUOUS_OHLC_PATH";
  } | null;
};
```

Bu tip mevcut backend sözleşmesinin anonimleştirilmiş özetidir. Araştırma sırasında yeni alanlar önerilebilir ancak mevcut sözleşme doğrudan değiştirilecekmiş gibi varsayım yapma.

## 3. P1.05.c araştırma amacı

P1.05.c’de henüz grafik implementasyonu yapılmayacak.

Amaç:

1. Güvenli bir canonical OHLCV chart data sözleşmesi gerekli mi?
2. Bar verisi mevcut simulation response’a mı eklenmeli?
3. Ayrı bir endpoint veya ayrı bir read-only chart DTO’su mu kullanılmalı?
4. Action marker’ları hangi canonical alanlara bağlanmalı?
5. `INDETERMINATE` ve ambiguous OHLC path durumları grafik üzerinde nasıl gösterilmeli?
6. Grafik yanlışlıkla kesin intrabar işlem sırası veya kesin fill zamanı ima eder mi?
7. Grafik hangi sonraki mikro fazlara bölünmeli?
8. P1.05.c’de yalnız sözleşme mi hazırlanmalı, yoksa minimal statik grafik de kabul edilebilir mi?

## 4. Araştırılacak ana konular

### A. Canonical OHLCV bar DTO

Aşağıdaki alanların gerekliliğini araştır:

- `bar_index`
- `open_time_us`
- `close_time_us`
- `open`
- `high`
- `low`
- `close`
- `volume`
- `is_closed`
- dataset kimliği
- model kimliği
- artifact/config revision
- period start/end
- processed bar count

Her alan için şunları belirt:

- Kullanıcı faydası
- Teknik gereklilik
- Veri sözleşmesi riski
- Precision riski
- Payload maliyeti
- P1.05.c için gerekli olup olmadığı
- ACCEPT / SIMPLIFY / DEFER / REJECT kararı

Özellikle şu noktaları açıklığa kavuştur:

- OHLCV finansal decimal alanları string mi olmalı?
- `bar_index` integer olarak taşınabilir mi?
- `open_time_us` number, string veya BigInt gerektirir mi?
- ISO 8601 alanı mevcut sözleşmeye eklenmeli mi?
- Frontend tarih dönüşümü güvenli nasıl yapılmalı?
- `volume` P1.05.c için gerçekten gerekli mi?
- `is_closed` backend garantisi olarak mı tutulmalı?
- Barların sırası nasıl deterministik garanti edilmeli?
- Duplicate veya geriye giden `bar_index` nasıl ele alınmalı?
- Dataset kimliği ve artifact revision her chart payload’ında bulunmalı mı?

Frontend finansal decimal değerleri `Number`, `parseFloat`, `toFixed`, binary floating point aritmetiği veya frontend PnL/fee/equity hesabı kullanmamalıdır. Bu sınırları destekleyen resmi teknik kaynakları belirt.

### B. Endpoint mi, response genişletmesi mi?

Şu seçenekleri karşılaştır:

1. Mevcut simulation response’a `bars` alanı eklemek
2. Ayrı read-only `/chart-data` endpoint’i
3. Ayrı `GET /historical-runs/{id}/chart` endpoint’i
4. Aynı request içinde chart data döndürmek
5. Backend’in yalnız seçili aralık için bounded chart DTO üretmesi
6. Chart data’yı frontend’in mevcut action veya dataset kaynağından türetmesi

Her seçenek için tablo oluştur:

- Veri tekrar riski
- API sözleşmesi etkisi
- Payload boyutu
- Cache/persistence etkisi
- Security/privacy riski
- Stale dataset/config riski
- `INDETERMINATE` yönetimi
- Test maliyeti
- P1.05.c uygunluğu

Önemli sınır:

- P1.05.c’de yeni endpoint veya response genişletmesi otomatik kabul edilmiş değildir.
- Araştırma, hangi seçeneğin sonraki faza bırakılacağını gerekçelendirmelidir.
- P1.05.b action table mevcut sözleşmeyle çalışmaya devam etmelidir.
- Chart data action table’ın yerine geçmemelidir.

### C. Action marker sözleşmesi

Mevcut action alanları:

```typescript
type ActionMarkerSource = {
  bar_index: number;
  open_time_us: number;
  role: string;
  raw_reference: string;
  fill_price: string;
  quantity: string;
  fee: string;
};
```

Araştır:

- Marker yalnız `bar_index` ile mi eşleşmeli?
- `open_time_us` marker konumu için güvenilir mi?
- `fill_price` grafik koordinatı için kullanılabilir mi?
- `raw_reference` marker seviyesinde gösterilmeli mi?
- Marker, gerçek fill’i mi yoksa model aksiyonunu mu temsil eder?
- `SAFETY:1` gibi backend rolleri nasıl gösterilmeli?
- Unknown role nasıl ele alınmalı?
- Bir bar içinde ikinci action gelirse ne yapılmalı?
- Action ile bar eşleşmezse chart nasıl fail-closed davranmalı?
- Marker kullanıcıya kesin intrabar zaman veya sıra izlenimi verir mi?
- Marker tooltip’i finansal hesap yapmadan hangi alanları göstermeli?

Şu kuralı değerlendir:

> Marker yalnız backend action kaydı mevcutsa çizilebilir; frontend yeni action veya işlem üretmemelidir.

### D. INDETERMINATE / AMBIGUOUS davranışı

Mevcut modelde:

- Safety ve TP aynı OHLC barında erişilebiliyorsa intrabar sıra bilinmez.
- Ambiguous bar commit edilmeden sonuç `INDETERMINATE` olabilir.
- Ambiguous bar’dan sonra kesin action geçmişi üretilmemelidir.
- `OPEN_AT_END` kapanmış pozisyon anlamına gelmez.
- Funding `NOT_MODELED` olabilir.
- Mark `NOT_AVAILABLE` olabilir.
- Forced close uygulanmayabilir.

Araştır:

1. `INDETERMINATE` durumda grafik tamamen gizlenmeli mi?
2. Ambiguous bar’a kadar olan barlar gösterilebilir mi?
3. Ambiguous bar grafik üzerinde nasıl işaretlenmeli?
4. Ambiguous bar’dan sonraki barlar gösterilebilir mi?
5. Marker tamamen gizlenmeli mi?
6. “Belirsiz sonuç” banner’ı grafik üzerinde nasıl görünmeli?
7. Grafik, belirsiz sonucu başarı gibi göstermeden nasıl kullanılabilir?
8. `OPEN_AT_END` grafik üzerinde nasıl nötr gösterilmeli?
9. Unrealized veya equity çizgisi gösterilmeli mi?
10. Funding/mark modellenmiyorsa chart tooltip’inde ne yazmalı?

Minimum güvenlik açısından şu seçenekleri değerlendir:

- Grafik yok
- Yalnız veri görünümü
- Ambiguous bar öncesi sınırlı grafik
- Tüm barlar ama marker yok
- Tüm barlar + belirsizlik overlay’i

Her seçenek için yanlış finansal yorum riskini belirt.
