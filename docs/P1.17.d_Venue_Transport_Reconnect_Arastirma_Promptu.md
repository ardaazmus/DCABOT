# P1.17.d — Venue-specific transport mapping ve reconnect/catch-up araştırma promptu

## Araştırma görevi

Yerel Windows/Python 3.13 uygulamasında kullanılabilecek **tek bir public, read-only market-data venue profilini** seç ve bu profilin REST/ WebSocket transport, payload mapping, event-time, sequence, stale, gap, reconnect/catch-up ve offline fallback davranışlarını güncel resmi kaynaklarla kanıtla.

Bu çalışma uygulama kodu değildir. Amaç, P1.17.e’de yazılabilecek sınırlı bir public observation adapter için karar verilebilir ve denetlenebilir bir sözleşme üretmektir.

Araştırmacı teslim edilen rapordaki iddiaları otomatik doğru kabul etmemelidir. Her önemli iddia güncel resmi birincil kaynakla yeniden kontrol edilmeli; kaynakta bulunmayan davranışlar `NOT_VERIFIED` veya `DEFER` olarak bırakılmalıdır.

## 1. Uygulama bağlamı ve güvenlik sınırı

Anonim yerel uygulama bağlamı:

- Windows üzerinde Python 3.13.
- Offline-first yerel uygulama.
- Doğrulanmış tarihsel OHLCV dosyasıyla offline simülasyon zaten vardır.
- Public piyasa verisi yalnız **read-only observation** olarak alınabilir.
- Public observation; candidate, order, fill, balance, reserve, PnL veya historical-run sonucu değildir.
- P1 kapsamında private account, credential, API key, secret, gerçek emir, testnet emri, para hareketi ve canlı ekonomik fill yoktur.
- Ekonomik hesap sınırı `Decimal`/exact domain arithmetic’tir; `float` ekonomik authority olamaz.
- Tarihsel run identity’si ile live/public observation identity’si kesinlikle ayrıdır.

Araştırmada şunları isteme veya kullanma:

- repo adı, yerel klasör yolu, kullanıcı adı veya makine bilgisi;
- API key, private key, secret, token, cookie veya credential;
- özel hesap, bakiye, gerçek emir veya kişisel veri;
- private/authenticated endpoint örneği;
- gerçek emir gönderen kod;
- credential isteyen canlı bağlantı testi;
- uygulanmamış ekonomik formül veya sahte kesin PnL.

## 2. Venue seçimi için bağlayıcı kural

En fazla iki aday venue resmi kaynaklarıyla kısa karşılaştırılabilir; ancak rapor sonunda **tek bir seçilmiş public profile** bulunmalıdır.

Seçilen profil şu şartları sağlamıyorsa `NO-GO` yaz:

1. Kimlik bilgisi istemeyen public market-data yolu vardır veya kimliksiz olduğu resmi kaynakta açıkça gösterilmiştir.
2. Payload alanları ve timestamp birimleri resmi dokümanda tanımlıdır.
3. Symbol/product kapsamı açıkça tanımlıdır.
4. Duplicates, sequence, out-of-order veya gap davranışı için resmi kanıt ya da açıkça `NOT_VERIFIED` kaydı vardır.
5. Reconnect sonrası snapshot/catch-up/resubscribe davranışı resmi kaynakla veya açık `NOT_VERIFIED` kararıyla ayrıştırılabilir.
6. Uygulama, public observation’ı economic fill olarak sunmadan salt-okunur biçimde çalışabilir.

Venue örneği olarak Coinbase Advanced Trade public market-data WebSocket, Bybit V5 public trade/market stream veya başka bir resmi venue incelenebilir; ancak aday adı, mevcut proje için evrensel veya nihai entegrasyon kararı gibi sunulamaz. Binance historical archive kaynağı live feed için otomatik kanıt sayılmaz.

- sayfa başlığı;
- ürün/API sürümü;

Blog, forum, üçüncü taraf SDK, Stack Overflow, genel backtesting yazısı veya kod deposu; venue’nin güncel protokol kuralı için birincil kanıt yerine kullanılamaz. Üçüncü taraf kaynak yalnız keşif girdisi olabilir ve `SECONDARY / NOT_AUTHORITY` olarak etiketlenmelidir.

Kaynakta yazmayan rate limit, timeout, stale threshold, retry count, sequence continuity, snapshot garantisi veya fill sonucunu resmi venue davranışı gibi yazma.

## 5. Seçilen public profile’ın canonical mapping’i

Seçilen venue için gerçek örnek payload’ı resmi kaynaktan alıntılamadan, alanları tabloyla eşleştir:

| Canonical alan | Venue alanı | Zorunlu mu? | Birim/tip | Dönüşüm | Kaynak |
|---|---|---:|---|---|---|
| `source_id` | venue/profile sabiti | evet | identifier | sabit profile id | kaynak |
| `transport` | REST/WS | evet | enum | explicit enum | kaynak/policy |
| `symbol` | venue symbol | evet | identifier | allowlist | kaynak |
| `product` | spot/perpetual vb. | evet | profile enum | allowlist | kaynak |
| `event_id` | trade/message/event id | evet veya `NOT_VERIFIED` | identifier | canonical string | kaynak |
| `source_sequence` | seq/update id | opsiyonel veya zorunlu | integer | positive integer | kaynak |
| `event_time_us` | trade/event timestamp | evet | integer microseconds | exact unit conversion | kaynak |
| `receive_time_us` | local receipt time | uygulama alanı | integer microseconds | caller clock | application policy |
| `processing_time_us` | local processing time | uygulama alanı | integer microseconds | caller clock | application policy |
| `price` | venue price | evet | decimal string | exact parse | kaynak/policy |
| `quantity` | venue quantity | evet/`NOT_VERIFIED` | decimal string | exact parse | kaynak/policy |
| `payload_hash` | raw normalized payload | evet | SHA-256 hex | canonical serialization | application policy |

Aşağıdaki noktaları özellikle çöz:

1. Venue numeric alanları JSON number mı, decimal string mi, ölçekli integer mı?
2. JSON number ise binary float kullanmadan exact parse nasıl yapılır?
3. Timestamp saniye, milisaniye, mikrosaniye veya nanosaneye göre nasıl doğrulanır?
4. Yanlış timestamp unit’i yanlışlıkla kabul edilirse hangi fail-closed durum üretilir?
5. `event_id` yoksa sequence tek başına yeterli midir; değilse local identity hangi açık policy ile üretilir?
6. Bir WebSocket mesajında birden fazla trade varsa her trade ayrı observation mıdır?
7. Aynı `seq` içinde birden fazla kayıt mümkün mü?
8. Snapshot ve incremental update birbirinden nasıl ayrılır?
9. REST snapshot ile WebSocket event aynı canonical observation olarak birleştirilebilir mi, yoksa farklı transport identity mi gerekir?

## 6. Zaman taksonomisi ve saat otoritesi

Rapor şu dört zamanı birbirine karıştırmadan tanımlamalıdır:

- `event_time_us`: venue/source olayının zamanı;
- `receive_time_us`: yerel istemcinin payload’ı aldığı zaman;
- `processing_time_us`: yerel uygulamanın payload’ı normalize ettiği zaman;
- `persistence_time_us`: varsa yerel kalıcı kayıt zamanı.

Zorunlu kararlar:

- Source event time hiçbir koşulda receive/processing time ile değiştirilemez.
- Stale hesabında hangi zaman kullanılır ve bunun resmi venue davranışı mı yoksa application policy mi olduğu açıkça yazılır.
- Sistem saati geri giderse veya güvenilmezse observation kabul edilir mi?
- Future-dated event, negative latency ve `processing_time_us < receive_time_us` nasıl ele alınır?
- UTC normalization ve integer microsecond dönüşümü tam olarak nasıl yapılır?
- Aynı event time’a sahip iki farklı observation geçerli olabilir mi?

Venue kaynağında bulunmayan bir stale eşiğini venue gerçeği olarak yazma. Önerilen eşik yalnız `SYNTHETIC_APPLICATION_POLICY` olarak etiketlenebilir.

## 7. State machine: bağlantı, tazelik ve gap

Minimum state machine’i açık transition tablosuyla ver:

```text
DISCONNECTED
  -> CONNECTING
  -> SYNCED
  -> STALE
  -> GAP
  -> RECONNECTING
  -> SYNCED veya FAILED
```

Gerekliyse `QUARANTINED` veya `RESYNC_REQUIRED` eklenebilir; her ek state’in owner’ı ve çıkış şartı yazılmalıdır.

Her transition için şu alanları doldur:

| Current | Input/event | Guard | Next state | Observation kabulü | Economic authority |
|---|---|---|---|---|---|

Zorunlu durumlar:

1. İlk bağlantı ve ilk geçerli observation.
2. Heartbeat var ama market event yok.
3. Stale threshold tam sınırında ve bir birim üzerindeyken.
4. TCP/WebSocket kapanması.
5. Malformed JSON veya schema mismatch.
6. Wrong symbol/product.
7. Sequence gap.
8. Sequence geriye gidiyor veya out-of-order geliyor.
9. Aynı event id tekrar geliyor.
10. Aynı event id farklı payload ile geliyor.
11. Reconnect sonrası eski event geliyor.
12. Reconnect sonrası snapshot/catch-up geliyor.
13. Gap doldurulamıyor.
14. Uygulama kapanıp yeniden açılıyor.

Bağlayıcı fail-closed kuralı:

> Gerekli market state stale, gap, conflict, malformed veya resync-required durumundaysa yeni observation ekonomik fill değildir ve simulated economic transition tetikleyemez.

## 8. Sequence, duplicate ve out-of-order politikası

Seçilen venue’nin resmi davranışına göre şu matrisi doldur:

| Durum | Örnek | Kabul sonucu | Cursor state | Replay sonucu |
|---|---|---|---|---|
| Exact duplicate | aynı id + aynı immutable payload | no-op | değişmez | toplam değişmez |
| Conflicting duplicate | aynı id + farklı payload | fail-closed | `FAILED` veya kaynakla kanıtlı state | kayıt eklenmez |
| Expected next sequence | `n -> n+1` | kabul | `SYNCED` | bir kayıt eklenir |
| Sequence gap | `n -> n+2` | quarantine | `GAP` | sonraki event resync ister |
| Lower sequence | `n -> n-1` | quarantine | `GAP` | kayıt eklenmez |
| Missing sequence | önce var, sonra yok | `NOT_VERIFIED` veya fail-closed | açıkça yaz | ekonomik geçiş yok |
| Late event | event time daha eski | quarantine/reconciliation | açıkça yaz | sonuç overwrite yok |

Venue dokümanı duplicate veya gap davranışını belirtmiyorsa bunu uygulama gerçeği gibi tamamlamayın; `NOT_VERIFIED` bırakın ve adapter kararını `DEFER` edin.

## 9. Reconnect ve catch-up

Seçilen profile için resmi olarak şu soruların cevabını bul:

1. Client yeniden bağlandığında yeniden subscribe zorunlu mu?
2. Yeni bağlantı önce snapshot mı, incremental event mi alır?
3. Sequence başlangıcı nasıl belirlenir?
4. Kaybolan event’ler REST snapshot, WebSocket snapshot, sequence range veya başka bir yöntemle doldurulabilir mi?
5. Catch-up yoksa sistem yeni runtime segmenti başlatmalı mı?
6. Eski segmentin son observation’ı ile yeni segmentin ilk observation’ı nasıl ayrılır?
7. Reconnect sırasında gelen duplicate olaylar nasıl no-op yapılır?
8. Reconnect sırasında gelen daha eski olaylar nasıl reddedilir?
9. Reconnect retry/backoff değerleri resmi venue kuralı mı, application policy mi?
10. Resync başarısızsa `GAP`, `STALE`, `FAILED` veya `INDETERMINATE` hangisi seçilir ve neden?

Aşağıdaki davranışları birbirine karıştırma:

- `RESUBSCRIBE`: bağlantı protokolü işlemi;
- `RESYNC`: market state’in doğrulanması;
- `REPLAY`: local kayıtların yeniden oynatılması;
- `RECONCILIATION`: eksik/çakışan olayların çözüm süreci.

Resync tamamlanmadan `SYNCED` veya ekonomik acceptance iddiası kurma.

## 10. Offline fallback ve historical ayrımı

Açık bir fallback hiyerarşisi ver:

```text
verified historical artifact
        -> local historical simulation / local observation replay
        -> no network required

live public feed failure
        -> stale/gap/failed observation state
        -> no silent continuation as live data
        -> no historical result overwrite
```

Zorunlu kararlar:

- Network yokken verified historical cache hangi koşullarda çalışır?
- Live feed başarısızken historical cache “live replacement” gibi gösterilebilir mi? Cevap `HAYIR` olmalı; gerekçeyi yaz.
- Live observation replay’i historical run identity’sinden nasıl ayrı tutulur?
- Cache artifact hash’i live event identity yerine kullanılabilir mi?
- Live observation’lar persistence’a yazılacaksa hangi fazda ve hangi immutable schema ile? Bu fazda implementation kararı verme; `DEFER` yaz.

## 11. Observation → simulated adapter sınırı

Bu araştırma ekonomik fill modeli seçmeyecektir. Sadece aşağıdaki sınırı kesinleştirecektir:

```text
public payload
  -> normalized observation
  -> feed cursor acceptance
  -> optional candidate input (future phase only)
  -> simulated economic acceptance (future phase only)
```

Şu durumlarda simulated fill üretilemeyeceğini yaz:

- stale veya gap state;
- conflicting duplicate;
- source sequence bilinmiyor ve policy bunu gerektiriyor;
- price/quantity exact parse edilemiyor;
- symbol/product profile ile uyuşmuyor;
- event time unit’i belirsiz;
- spread/slippage/fee/latency/queue/volume participation modeli seçilmemiş;
- live public ticker, historical OHLCV ile aynı authority sanılıyor;
- intra-bar path veya execution timing gözlemlenemiyor.

Public observation’ın response/persistence metadata’sında aşağıdaki işaretlerin ayrı taşınmasını öner veya reddet:

- `READ_ONLY`;
- `PUBLIC_MARKET_DATA`;
- `SIMULATED`;
- `NO_CREDENTIAL`;
- `NO_REAL_ORDER`.

Bu işaretler ekonomik doğruluk kanıtı değildir; yalnız scope/capability metadata’sıdır.

## 12. Güvenlik ve veri bütünlüğü

Seçilen transport için şu sınırları resmi kaynak ve application policy olarak ayır:

- HTTPS/WSS only;
- exact host/path allowlist;
- redirect davranışı;
- TLS hostname doğrulaması;
- response/message size sınırı;
- decompression veya nested payload sınırı;
- malformed payload reddi;
- symbol/product allowlist;
- payload canonicalization ve hash;
- log redaction;
- URL/path/credential hata sızıntısı;
- retry/backoff ve retry bütçesi;
- in-memory bounded buffer;
- cache publication’ın doğrulama tamamlanmadan görünür olmaması;
- crash sonrası local replay sınırı.

Bu maddelerden resmi venue kaynağıyla kanıtlanmayanlar `APPLICATION_POLICY` veya `NOT_VERIFIED` olarak etiketlenmelidir.

## 13. Bağımsız oracle ve test matrisi

Production kodunu import etmeyen küçük bir Python 3.13 stdlib oracle veya ayrıntılı pseudocode ver. Oracle network’e bağlanmamalı, credential almamalı ve ekonomik hesap yapmamalıdır.

Her fixture için expected ve unexpected sonuç ver:

| Fixture | Expected | Unexpected | Oracle alanları |
|---|---|---|---|
| first valid observation | `SYNCED` + accepted | fill/order | state, count |
| exact duplicate | no-op | ikinci acceptance | cursor equality |
| conflicting duplicate | fail-closed | overwrite | state, count |
| expected sequence | accepted | gap | sequence |
| sequence gap | `GAP` | silent continuity | state, count |
| lower/out-of-order sequence | quarantine | reorder by receive time | state |
| stale boundary | exact boundary policy | implicit wall-clock | state |
| malformed payload | rejected | numeric zero fallback | error/state |
| wrong symbol/product | rejected | cross-scope acceptance | scope |
| reconnect without resync | blocked | `SYNCED` | state |
| explicit successful resync | new segment | old sequence continuation | segment/cursor |
| unrecoverable gap | `FAILED`/`GAP`/`INDETERMINATE` | silent recovery | state |
| network failure + verified historical cache | local historical path only | live-state pretending | source mode |
| same live data replayed twice | same observation outcomes | new economic fills | outcome tuple |
| live observation vs historical run | separate identity | overwrite/equality assumption | identity fields |

Zorunlu metamorphic özellikler:

- Exact duplicate eklemek accepted observation sayısını ve cursor’ı değiştirmez.
- Aynı input tuple aynı outcomes/cursor üretir.
- Receive time değişip immutable payload aynı kalırsa duplicate kararı bozulmaz.
- Sequence gap sonrası resync yoksa sonraki event’ler otomatik olarak accepted olmaz.
- Replay çıktısında `run_id`, `result_id`, `pnl`, `order_id`, `fill_id` veya reserve alanı oluşmaz.
- Historical artifact hash’i live observation event identity’sine dönüşmez.

## 15. Karar matrisi

Her ana alanı aşağıdaki etiketlerden biriyle bitir:

- `ACCEPT`: resmi kaynak + local uygulanabilirlik + bağımsız oracle yeterli;
- `ACCEPT_WITH_LIMITATION`: yalnız read-only observation/local replay sınırı;
- `DEFER`: eksik mapping, catch-up veya policy kararı;
- `NO-GO`: yanlış ekonomik/operasyonel iddia riski;
- `NOT_VERIFIED`: resmi kanıt bulunamadı.

Raporun sonunda aşağıdaki kararları açıkça ver:

1. Seçilen tek venue/profile nedir?
2. REST hangi bounded kullanım için uygundur?
3. WebSocket hangi bounded kullanım için uygundur?
4. P1 için ilk adapter transport’u hangisidir ve neden?
5. Canonical event schema tam olarak nedir?
6. `event_time_us`, `receive_time_us`, `processing_time_us` authority’si nedir?
7. Sequence gap hangi state’i üretir?
8. Duplicate ve conflicting duplicate nasıl ayrılır?
9. Reconnect sonrası hangi kanıtla `SYNCED` olunabilir?
10. Catch-up yoksa hangi state ve hangi yeni segment politikası kullanılır?
11. Stale threshold resmi venue davranışı mı, application policy mi?
12. Offline historical cache hangi koşulda çalışır?

14. P1.17.e implementation için gerekli kalan kanıtlar nelerdir?
15. Hangi davranışlar kesinlikle `DEFER` veya `NO-GO` kalmalıdır?

## 16. Implementation gate

Araştırma sonucu şu kapıyla bitmelidir:

### ACCEPT_WITH_LIMITATION olabilir

- yalnız bir resmi public profile seçilmişse;
- source/symbol/product/time/numeric mapping açıkça kanıtlanmışsa;
- observation ve economic fill ayrımı korunuyorsa;
- duplicate/conflict/gap/stale/reconnect state’leri fail-closed ise;
- offline replay bağımsız oracle ile tekrar üretilebiliyorsa;
- credential ve gerçek emir yolu yoksa.

### DEFER zorunludur

- REST/WS payload mapping eksikse;
- reconnect sonrası catch-up/snapshot davranışı bilinmiyorsa;
- sequence veya event identity eksikliği çözülmemişse;
- stale threshold yalnız varsayım olarak kalıyorsa;
- venue profile seçimi iki aday arasında kapanmıyorsa;
- local persistence veya API/UI sözleşmesi ayrıca araştırılmadıysa.

### NO-GO zorunludur

- public observation ekonomik fill olarak sunulacaksa;
- stale/gap verisi sessizce canlı ve geçerli kabul edilecekse;
- receive time source event time yerine kullanılacaksa;
- credential veya gerçek emir yolu gerekecekse;
- live data historical run sonucunu overwrite edecekse;
- float veya cross-unit numeric hesap önerilecekse;
- reconnect başarısızlığı temiz/sürekli market state gibi raporlanacaksa.
