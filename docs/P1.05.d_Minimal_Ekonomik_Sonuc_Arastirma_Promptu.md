# P1.05.d — Minimal Ekonomik Sonuç Özeti Araştırma Promptu

Aşağıdaki anonim yerel Python 3.13 + FastAPI ve React/TypeScript finansal simülasyon uygulaması için **P1.05.d minimal ekonomik sonuç özeti** konusunda güncel, kaynaklı, teknik ve UI/UX odaklı araştırma yap.

Bu araştırma bir ürün fikri üretme çalışması değildir. Amaç, mevcut tarihsel simülasyon response’unda zaten bulunan ekonomik alanların kullanıcıya en küçük, dürüst, finansal olarak yanlış yönlendirmeyen ve frontend’de yeniden hesap yapılmasını gerektirmeyen görünümünü belirlemektir.

Rapor yalnız aşağıdaki anonim sözleşme ve sınırlar üzerinden hazırlanmalıdır. Herhangi bir gerçek kullanıcı hesabı, credential, özel dosya, özel URL, proje adı, yerel yol veya gizli bilgi isteme.

## 1. Bağlam ve faz sırası

Uygulama yerel makinede çalışan bir tarihsel finansal simülasyon demosudur:

- Python 3.13 + FastAPI backend
- React + TypeScript frontend
- Yerel ve salt-okunur çalışma
- Public veya local historical OHLCV dataset
- Gerçek hesap, gerçek emir, testnet veya live venue bağlantısı yok
- Credential/API key yok
- Sonuçlar şu anda kalıcı olarak kaydedilmiyor
- Amaç yatırım tavsiyesi veya canlı performans iddiası üretmek değil; simülasyonun hangi varsayımlarla ne ürettiğini dürüstçe göstermektir

Faz sırası bağlayıcıdır:

1. P1: tam yerel UI + geçmiş veri demo
2. P2: Binance testnet
3. P3: gerçek Binance kurulumu
4. P4: diğer borsalar

P1.05’in şu alt parçaları tamamlandı:

- P1.05.a: mevcut tarihsel simülasyon sonucunun minimal güvenli özeti
- P1.05.b: mevcut action geçmişinden salt-okunur işlem/aksiyon tablosu
- P1.05.c.1: bounded canonical OHLC chart-data sözleşmesi
- P1.05.c.2: native inline SVG ile statik, nötr OHLC overview
- P1.05.c.3: `simulation.actions` ile chart bar’larını eşleştiren statik, nötr, fail-closed action marker

Bu araştırmanın konusu **P1.05.d**: ekonomik sonucu daha iyi anlamak için mevcut backend alanlarının en küçük güvenli sunumudur.

## 2. Araştırmanın kesin amacı

Tek bir uygulanabilir minimum öneri ver:

- Kullanıcı tamamlanmış tarihsel simülasyonun ekonomik sonucunu hangi 3–6 bilgiyle anlayabilir?
- Hangi alanlar mevcut response’tan hiçbir hesap yapılmadan gösterilebilir?
- Hangi alanların tanımı mevcut veri/varsayım sınırları nedeniyle belirsiz veya koşullu gösterilmelidir?
- `OPEN_AT_END`, `NOT_MODELED` funding, `NOT_AVAILABLE` mark ve `persisted=false` nasıl görünür kılınmalıdır?
- `realized_net_after_all_costs`, `fees`, `realized_gross`, `unrealized` ve `equity` aynı ekranda nasıl karıştırılmadan ayrıştırılmalıdır?
- Hangi metrikler bu küçük faza kesinlikle alınmamalıdır?
- Frontend’de hiçbir finansal aritmetik yapılmadan bu görünüm uygulanabilir mi?
- Mevcut response yeterli değilse eksikliği açıkça belirt; varsayımsal yeni alan veya hesap uydurma.

Araştırma, büyük dashboard, equity curve, risk terminali veya performans analizi tasarlamamalıdır. En küçük anlaşılır sonuç kartı/özet grubu araştırılmalıdır.

## 3. Mevcut tarihsel simülasyon response sözleşmesi

Frontend’in aldığı tamamlanmış veya belirsiz sonuç kavramsal olarak aşağıdaki şekildedir. Bu alanlar backend tarafından üretilir; frontend bunları tekrar hesaplamaz.

```ts
type HistoricalSimulationResult = {
  execution_status: "COMPLETED" | "INDETERMINATE";
  application_code: "AMBIGUOUS_OHLC_PATH" | null;
  persisted: false;
  dataset: {
    dataset_id: string;
    artifact_sha256: string;
    period_start: string;
    period_end: string;
    processed_bar_count: number;
  };
  config: {
    schema_version: 1;
    config_hash: string;
  };
  assumptions: {
    model: "historical_ohlcv_v1";
    bar_visibility: "CLOSED_ONLY";
    intrabar_path: "NOT_INFERRED";
    max_actions_per_bar: 1;
    fee_model: string;
    slippage_model: string;
    funding: "NOT_MODELED";
    exchange_mark: "NOT_AVAILABLE";
    force_close_at_end: boolean;
  };
  actions: Array<{
    bar_index: number;
    open_time_us: number;
    role: string;
    raw_reference: string;
    fill_price: string;
    quantity: string;
    fee: string;
  }>;
  summary: {
    symbol: string;
    qty: string;
    cost: string;
    realized_gross: string;
    fees: string;
    funding: string;
    realized_net_after_all_costs: string;
    unrealized: string | null;
    equity: string;
    anchor: string | null;
    take_profit_price: string | null;
    entry_notional: string;
    position_status: "CLOSED" | "OPEN_AT_END";
    funding_status: "NOT_MODELED";
    mark_status: "NOT_AVAILABLE";
  };
  ambiguity: { bar_index: number; code: "AMBIGUOUS_OHLC_PATH" } | null;
};
```

Araştırma, bu sözleşmedeki alan adlarını değiştirmemeli ve mevcut alanları olduğundan daha kesin yorumlamamalıdır.

## 4. Önceki fazlarda bağlayıcı olarak kabul edilen güvenlik kararları

Aşağıdaki kararları yeniden açma; ekonomik özetin etkisini değerlendir:

- Domain/core ekonomik doğruluğun tek kaynağıdır.
- UI hesap yapmaz; backend’den gelen finansal string değerleri gösterir.
- Para ve miktar alanları decimal string olarak taşınır.
- JavaScript `Number` yalnız layout/grafik koordinatı gibi finansal olmayan sunum işlerinde kullanılabilir.
- `historical_ohlcv_v1` yalnız kapalı OHLCV barları işler.
- OHLC içi işlem sırası çıkarılamazsa sonuç `INDETERMINATE / AMBIGUOUS_OHLC_PATH` olur.
- Belirsiz sonuç başarı gibi gösterilmez.
- Aynı OHLC barında bilinmeyen sıra varsa ilgili bar commit edilmez.
- `OPEN_AT_END` gerçek kapanış değildir; forced close uygulanmaz.
- Funding modellenmemişse sıfır varsayılmaz ve “funding yok” gibi kesin bir finansal sonuç ima edilmez.
- Exchange mark mevcut değilse `unrealized`/equity alanlarının anlamı açıkça sınırlandırılır.
- `persisted=false` sonucu geçmişte kaydedilmiş veya tekrar üretilebilir kalıcı kayıt gibi gösterilmez.
- Gerçek performans, kârlılık garantisi, yatırım tavsiyesi veya canlı borsa eşdeğerliği iddia edilmez.
- Eksik/uyuşmayan/unknown veri sessizce tamamlanmaz.
- P1.05.d yeni kalıcı kayıt, export, yeni backend hesap motoru veya live/testnet yolu değildir.

## 5. Finansal anlam araştırması

Aşağıdaki alanların her biri için kaynaklı ve bağlama uygun değerlendirme yap:

1. `realized_gross`
2. `fees`
3. `funding`
4. `realized_net_after_all_costs`
5. `unrealized`
6. `equity`
7. `cost`
8. `qty`
9. `entry_notional`
10. `position_status`
11. `funding_status`
12. `mark_status`
13. `anchor`
14. `take_profit_price`

Her alan için şu soruları cevapla:

- Kullanıcıya gösterilmesi P1.05.d’de gerekli mi?
- Etiket nasıl yazılmalı?
- Değer doğrudan backend’den gösterilebilir mi?
- Değerin yanında hangi kısa varsayım/sınırlama notu gerekli?
- Bu değer realized, unrealized, cash/equity veya position state ile karışabilir mi?
- Funding/mark/forced-close eksikliği değeri koşullu hale getiriyor mu?
- Alan mevcut sözleşmede olmasına rağmen bu fazda `DEFER` edilmeli mi?

Özellikle aşağıdaki ayrımların yanlış karışmasını denetle:

- gross PnL ile net PnL
- realized sonuç ile unrealized değer
- işlem maliyeti ile başlangıç notional’ı
- pozisyon quantity’si ile hesap equity’si
- açık pozisyonun mark-to-market değeri ile gerçek kapanmış sonuç
- funding’in modellenmemesi ile funding’in sıfır olması
- forced close uygulanmaması ile dönem sonu kapanışı
- “sonuç” kelimesinin realized net sonucu mu yoksa equity’yi mi ifade ettiği

## 6. Mevcut alanların güvenilirliği ve gerekli backend değişikliği

Şu kararı net ver:

- P1.05.d yalnız mevcut `summary` alanlarını göstererek tamamlanabilir mi?
- Yeni bir backend endpoint gerekir mi?
- Mevcut response’a yeni alan eklemek gerekir mi?
- Backend alanlarının tanım dokümantasyonu yeterli değilse önce contract clarification mı gerekir?
- `unrealized` ve `equity` gibi alanlar `mark_status=NOT_AVAILABLE` iken gösterilebilir mi, yoksa yalnız “mevcut ama mark yok” şeklinde mi sunulmalıdır?
- `OPEN_AT_END` durumda `realized_net_after_all_costs` ve `unrealized` birlikte nasıl etiketlenmelidir?
- `CLOSED` durumda `unrealized=null` veya başka bir değer varsa hangi kullanıcı mesajı güvenlidir?
- `INDETERMINATE` durumda ekonomik özet tamamen gizlenmeli mi, yoksa yalnız kapsam/ambiguity bilgisi mi gösterilmelidir?

Yeni finansal formül veya backend hesap öneriyorsan, bunu P1.05.d minimum kapsamına otomatik dahil etme. `BLOCKED` veya `RESEARCH_REQUIRED` olarak işaretle ve gereken doğrulama girdisini belirt.

## 7. En küçük UI/UX görünüm araştırması

Mevcut ekran, tarihsel simülasyon sonucunda zaten şu bölümlere sahiptir:

- sonuç durum mesajı
- sonuç özeti
- dataset dönem/bar bilgisi
- model, config ve artifact kısa hash bilgisi
- statik OHLC grafik
- statik action marker
- action/trade table
- varsayımlar ve sınırlamalar

P1.05.d için şu minimum seçenekleri karşılaştır:

### A. Üç ana değer + durum

- Net gerçekleşmiş sonuç
- Fee
- Pozisyon durumu
- Ayrı kısa sınırlama notu

### B. Gross/net/fee ayrımı

- Brüt gerçekleşen
- Fee
- Net gerçekleşen
- Açık pozisyon notu

### C. Gerçekleşen + açık pozisyon ayrımı

- Net gerçekleşen sonuç
- Açık pozisyon/unrealized, yalnız koşullu etiketle
- Equity, yalnız anlamı güvenli ise
- Pozisyon durumu ve mark/funding açıklaması

### D. Mevcut alanların tamamını listeleyen ayrıntı paneli

Bu seçeneğin bilişsel yük, yanlış kesinlik ve finansal karışıklık riskini değerlendir. P1.05.d için tek minimum seçeneği seç; diğerlerini `DEFER` veya `REJECT` gerekçesiyle ayır.

UI araştırması şu durumları ayrı değerlendirmelidir:

- `COMPLETED + CLOSED`
- `COMPLETED + OPEN_AT_END`
- `INDETERMINATE + AMBIGUOUS_OHLC_PATH`
- simulation API error / no result
- chart ready fakat ekonomik alanlar eksik/uyuşmuyor
- funding `NOT_MODELED`
- mark `NOT_AVAILABLE`
- persisted `false`
- action count sıfır
- çok uzun decimal string
