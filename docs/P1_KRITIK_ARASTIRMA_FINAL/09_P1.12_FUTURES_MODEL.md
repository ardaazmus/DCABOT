## 7. Asset/unit/precision/rounding
Economic inputs are parsed from decimal strings or exact integers. Internal arithmetic may use Decimal/Fraction; venue quantization occurs at the declared order/fee/margin boundary, never at UI formatting. Asset/unit tags are mandatory for qty, notional, fee, funding, margin and reserve. Rounding mode is part of the model/profile identity; missing rounding owner fails closed.

## 8. Time, ambiguity, EOF, gap, duplicate, late event
Historical economic ordering uses event/bar/effective time, not processing time. Ambiguity cannot invent a suffix; only committed prefix survives. EOF is an explicit outcome rather than an implicit fill. Known duplicate is idempotent; conflicting duplicate becomes CONFLICT; genuinely new late event enters reconciliation/recovery. Feed/data gaps are explicit STALE/GAP/INDETERMINATE states unless a versioned repair transform exists.

## 9. Core/API contract etkisi
Core owns acceptance and economic mutation. API returns typed exact numeric strings, explicit state/result taxonomy, model/profile/version/hash identities, and source/effective times. API must not expose a display-formatted value as economic authority. Unsupported/unknown/blocking fields remain tagged, not numeric zero.

## 10. Persistence/replay/hash etkisi
Persist event identity, economic payload, ordering/effective time, model/config/dataset/kernel/schema/canonicalization versions, and resulting state version. Replay must be deterministic under the same identity tuple. Canonical hash supports comparison but is not the only oracle; field-level independent comparison is required.

## 11. UI/UX ve yanlış yorum riski
UI renders backend-authoritative values and state labels. It must distinguish OPEN_AT_END/INDETERMINATE/STALE/CONFLICT from completed-valid results, and must not silently hide missing data or recompute PnL/reserve/risk. Risk severity cannot rely on color alone in accessibility-sensitive views.

## 1. Product separation

**REJECT:** Spot inventory ve futures position’ı tek state/formül olarak modellemek. Spot asset ownership transferidir; linear futures position settlement asset PnL, margin, funding ve liquidation state’i içerir. Spot fee asset bile side’a göre purchased asset olabilir [S14]; futures fee/funding/margin başka kurallara sahiptir [S15-S23].

Suggested discriminated union:
```text
SPOT_POSITION {base_inventory, quote_cash, cost_basis_policy}
LINEAR_FUTURES_POSITION {side, qty_base_or_contract, entry_price, settlement_asset, margin_mode, leverage_profile, margin_state, funding_ledger}
```

## 2. Linear PnL oracle
Bybit current FAQ linear USDT/USDC contracts için [S16]:
- long: `PnL = Q * (P_exit - P_entry)`
- short: `PnL = Q * (P_entry - P_exit)`
Settlement unit quote/settlement asset, **yalnız Q gerçekten base-equivalent contract quantity ise**. Contract multiplier farklıysa `Q_effective = contracts * contract_size` profile’dan gelir.

Independent fixture: Q=1.25000000, entry=40000, mark=42000 -> long UPL=2500.00000000 QUOTE_ASSET; short UPL=-2500.00000000 QUOTE_ASSET.

Leverage PnL’yi değiştirmez; required initial margin’i değiştirir [S16].

## 3. Price authorities
Bybit mark price’i index/basis kaynaklı ayrı fiyat olarak tanımlar; liquidation ve UPL ölçümünde kullanır [S18]. Last trade actual execution/PnL close price olabilir; index reference’tır; trigger price strategy/order profile’a göre seçilebilir.

**Invariant:** `mark_price`, `index_price`, `last_price`, `trigger_price` ayrı typed fields. UI bunları tek `price` alanına collapse etmez.

## 4. Funding
Bybit: funding belirli funding time’da pozisyon tutanlar arasında transfer edilir; positive rate’te long pays short, negative rate’te tersi; `Funding Fee = Position Value * Funding Rate`, USDT linear için `Position Value = Contract Quantity * Mark Price` [S17].

Fixture: Q=1.25000000, mark=42000, rate=0.0001 -> abs funding=5.250000000000 QUOTE_ASSET. Sign convention local ledger’da örn. payer negative, receiver positive.

**Do not synthesize** funding on every bar. Funding event timestamp/schedule data yoksa funding result `NOT_VERIFIED` veya disabled model.

## 6. Isolated vs cross
Isolated position margin independent allocation; cross shares account margin across positions. Bybit cross liquidation evaluates account IMR/MMR [S21], isolated uses position-specific liquidation price [S20]. **REJECT:** same liquidation reducer for both.

## 7. Liquidation
Bybit publishes detailed isolated liquidation formula [S20] and cross rules/formulas [S21], but these are product/version specific; 2025-2026 algorithm updates changed mark-price use. Therefore:
- external venue profile can encode exact documented formula/version;
- generic `FUTURES` profile cannot claim universal liquidation formula;
- missing risk-tier/MM deduction/fee-close inputs -> `NOT_VERIFIED`;
- partial liquidation behavior is venue-specific and must be separate transition, not generic full close.

## 8. Trading vs funding vs liquidation fees
Separate ledgers. Closed/realized PnL can include trading and funding fees [S15]; liquidation fee, if modeled, is an explicit liquidation event field and not ordinary trading fee unless venue contract says so.

## 9. Rounding/precision
Economic PnL in exact Decimal; instrument qty/price step quantization at order acceptance; venue-displayed liquidation rounding must not feed back into core threshold unless documentation specifies rounded threshold.

## 10. Restart/replay
Persist original accepted fills, funding events, margin profile version, mark/index observations used for risk, and liquidation event. Recompute with same profile version must yield canonical same result; changing venue profile is a new model identity.
