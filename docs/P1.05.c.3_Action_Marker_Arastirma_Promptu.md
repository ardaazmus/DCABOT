# P1.05.c.3 — Action Marker Araştırma Promptu

Aşağıdaki anonim yerel Python 3.13 + FastAPI ve React/TypeScript finansal simülasyon uygulaması için **P1.05.c.3 action marker** konusunda güncel, kaynaklı, teknik ve UI/UX odaklı araştırma yap.

Bu metin yalnızca araştırma isteğidir; proje talimatı değildir. Proje adı, klasör yolu, kullanıcı adı, gerçek hash, hesap bilgisi, API anahtarı, credential, özel config, yerel dosya yolu veya gerçek kullanıcı verisi isteme ve rapora koyma. Gerçek uygulama kaynak koduna erişimin yoksa bunu açıkça belirt; varsayımları doğrulanmış proje gerçeği gibi sunma.

## 1. Araştırma görevi

P1.05.c.1’de bounded canonical chart data contract, P1.05.c.2’de ise mevcut sözleşmeyi değiştirmeyen native inline SVG statik OHLC overview tamamlandı.

P1.05.c.3’ün araştırma amacı, action marker’ların bu statik tarihsel OHLC görünümüne eklenmesinin güvenli, dürüst, erişilebilir ve gerçekten gerekli minimum kapsamını belirlemektir.

Bu aşamada uygulama kodu yazılmayacak. Araştırma sonunda:

- marker gösteriminin P1.05.c.3’e alınıp alınmayacağı,
- marker’ın hangi mevcut veriye bağlanacağı,
- bar içi kesin zaman/sıra iddiasının nasıl engelleneceği,
- belirsizlik ve OPEN_AT_END davranışının ne olacağı,
- 320px’te marker yoğunluğunun nasıl yönetileceği,
- erişilebilirlik için marker dışında hangi metinsel fallback’in gerektiği,
- hangi özelliklerin sonraki faza bırakılacağı

karar verilmelidir.

Ana araştırma sorusu:

> Mevcut actions response’u ile P1.05.c.1 chart data contract’ını değiştirmeden, marker’ları yalnızca canonical bar_index konumuna bağlayarak güvenli ve minimal biçimde göstermek mümkün müdür?

## 2. Anonim sistem bağlamı

Uygulama şu sınırlara sahiptir:

- Windows üzerinde yerel çalışır.
- Backend Python 3.13 + FastAPI kullanır.
- Frontend React + TypeScript kullanır.
- Public tarihsel OHLCV dataset’i doğrulanmış yerel cache’ten okunur.
- P1’de public veri okuma/indirme ve offline demo olabilir.
- Testnet, canlı hesap, gerçek emir ve credential yolu bu kapsamda yoktur.
- Tarihsel simülasyon en fazla 1.000 kapalı bar işler.
- Model kimliği historical_ohlcv_v1’dir.
- Ekonomik doğruluk backend/domain katmanındadır.
- Frontend PnL, fee, equity, notional, pozisyon, getiri veya başka finansal hesap yapamaz.
- Grafik ve marker yalnız read-only tarihsel açıklama görünümüdür.
- Marker hiçbir işlem başlatmaz, karar üretmez veya emir sinyali vermez.
- Grafik/marker render’ı network, persistence, credential veya canlı borsa davranışı başlatmamalıdır.

## 3. Önceki fazlarda alınmış kararlar

Araştırma raporu aşağıdaki kararları yeniden açmamalıdır; yalnız marker etkilerini değerlendirmelidir.

### P1.05.b — Action table

Mevcut actions alanından read-only action/trade table tamamlandı.

Action kaynak alanları:

- bar_index
- open_time_us
- role
- raw_reference
- fill_price
- quantity
- fee

Action table kullanıcıya bar_index, ham backend role değeri, open_time_us, fill_price, quantity ve fee alanlarını gösterir. raw_reference varsayılan tabloda gösterilmez.

### P1.05.c.1 — Chart contract

Mevcut endpoint:

~~~text
GET /api/datasets/{dataset_id}/chart-data
~~~

Anonim TypeScript özeti:

~~~typescript
type HistoricalChartBar = {
  bar_index: number;
  open_time_us: number;
  close_time_us: number;
  open: string;
  high: string;
  low: string;
  close: string;
};

type HistoricalChartData = {
  dataset_id: string;
  artifact_sha256: string;
  model_id: "historical_ohlcv_v1";
  period_start: string;
  period_end: string;
  processed_bar_count: number;
  bars: HistoricalChartBar[];
};
~~~

Chart contract:

- strict/frozen backend DTO’su vardır,
- verified canonical barlardan türetilir,
- en fazla 1.000 bar döndürür,
- no-store taşır,
- volume, is_closed, marker veya run_id içermez,
- persistence oluşturmaz,
- path/credential taşımaz.

### P1.05.c.2 — Static OHLC overview

Mevcut render kararı:

- open sol tick’i,
- close sağ tick’i,
- kırmızı/yeşil yön semantiği yok,

- grafik tek bir accessible figure/image olarak tanımlanır,
- action table grafik tarafından kaldırılmaz.

## 4. Korunması zorunlu güvenlik kararları

Marker araştırması şu davranışları önermemelidir:

- INDETERMINATE sonuçta grafik ve marker gösterilmesi.
- AMBIGUOUS_OHLC_PATH veya eşdeğer ambiguity durumunda grafik/marker gösterilmesi.
- Belirsizlik öncesi barların veya marker’ların kısmi gösteriminin varsayılan yapılması.
- OPEN_AT_END için fake exit, forced close veya synthetic marker üretilmesi.
- Action/fill kaydının plan, intent, tahmin veya gelecek sinyali gibi gösterilmesi.
- Marker’ın fill zamanı veya intrabar işlem sırası hakkında kesinlik ima etmesi.
- Frontend finansal hesap yapılması.
- Frontend action/bar sırasını yeniden düzenlemesi.
- Geçersiz marker’ın sıfıra, ilk bara veya en yakın bara kaydırılması.
- 409 sonrası ilk N barın kesilerek gösterilmesi.
- Yeni marker endpoint’i, persistence veya run_id’nin otomatik eklenmesi.
- Action table’ın kaldırılması veya marker’ın tablo yerine sunulması.
- Dış CDN, dış script, telemetry, image URL veya network servisi kullanılması.

## 6. Canonical eşleştirme kararı

Mevcut karar:

- Marker’ın canonical birincil konumu bar_index’tir.
- open_time_us yalnızca ikincil tutarlılık metadata’sı olabilir.
- Marker’ın bar içindeki kesin x konumu çıkarılmaz.
- open_time_us ile fill saniyesi veya mikrosaniyesi üzerinden intrabar konum hesaplanmaz.
- OHLC içi işlem sırası çıkarılmaz.

Aşağıdaki seçenekleri karşılaştır:

1. Marker x konumu yalnız bar_index equal-slot.
2. Marker x konumu yalnız open_time_us time-scale.
3. bar_index anahtar, open_time_us consistency check.
4. Bar başlangıcına sabit marker.
5. Bar merkezine marker.
6. Open veya close tarafına marker.
7. Ayrı overlay layer’da aynı bar slotuna marker.
8. Marker’ı kendi timestamp’ine göre bar içinde konumlandırma.

Her seçenek için tablo oluştur:

- canonical sözleşmeye uygunluk,
- intrabar yanlış kesinlik riski,
- duplicate action riski,
- timestamp precision riski,
- 320px yoğunluk davranışı,
- responsive davranış,
- test maliyeti,
- accessibility maliyeti,
- P1.05.c.3 uygunluğu,
- ACCEPT / SIMPLIFY / DEFER / REJECT kararı.

Özellikle cevapla:

- Aynı bar_index için iki action gelirse ne yapılmalı?
- bar_index chart barları dışında kalırsa marker gizlenmeli mi?
- open_time_us bar timestamp’iyle uyuşmazsa marker gizlenmeli mi?
- Timestamp doğrulaması başarısızsa bar_index yine yeterli sayılabilir mi?
- 1-based bar_index sözleşmesi bozulursa tüm marker layer mı gizlenmeli, yoksa hatalı marker mı atlanmalı?
- Marker x coordinate’ı OHLC overview ile birebir aynı mapping’i nasıl paylaşmalı?
- Frontend sort yapmak neden yasak veya risklidir?

## 7. Marker dikey konumu

P1.05.c.2’de her bar low-high aralığı taşıyan nötr OHLC glyph olarak çizilir.

Şu seçenekleri karşılaştır:

1. Barın üstünde sabit offset.
2. Barın altında sabit offset.
3. open seviyesine bağlama.
4. close seviyesine bağlama.
5. fill_price seviyesine bağlama.
6. Y fiyat konumu vermeden yalnız x slotunda gösterme.
7. Barın üst/alt annotation lane’ine yerleştirme.

Kritik sorular:

- fill_price exact string’inin bar low-high domain’ine göre görsel eşlenmesi finansal hesap mıdır, display-only mapping midir?
- fill_price barın low-high aralığı dışında kalırsa ne yapılmalıdır?
- Fill price’ı bar içi kesin zamanla birleştirmek neden risklidir?
- Fill marker’ının belirli fiyat seviyesinde görünmesi kullanıcıya kesin fill seviyesi iddiası verir mi?
- Marker y konumu kullanıcıya işlem sırasını veya gerçek tick zamanını düşündürür mü?
- P1.05.c.3’te en güvenli minimum, yalnız bar slotu üst/alt marker’ı mıdır?

Varsayılan adayları sınıflandır:

- ACCEPT: yalnız bar slotuna bağlı nötr üst/alt marker; fiyat içi kesin konum iddiası yok.
- DEFER: fill_price’a göre y konumu; güvenli mapping ve yanlış yorum araştırması gerekir.
- REJECT: fill price ile intrabar kesinlik veya action sırası üretmek.

## 10. Belirsizlik ve OPEN_AT_END

- execution_status = INDETERMINATE ise chart ve marker yok.

- Belirsizlik öncesi action/marker gösterimi varsayılan değildir.

Şu soruları cevapla:

- Kısmi marker gösterimi hangi yanlış kesinlik riskini doğurur?

## 21. Son karar standardı

Rapor şu etiketleri açıkça kullanmalıdır:

### ACCEPT

P1.05.c.3’te gerçekten yapılacak minimum marker davranışı.

### SIMPLIFY

Daha küçük, daha güvenli ve daha az yanlış yorum üreten biçime indirilecek öneriler.

### DEFER

P1.05.c.4 veya sonraki fazlara bırakılacak özellikler:

- marker tooltip,
- hover,
- crosshair,
- zoom/pan,
- per-marker keyboard exploration,
- marker filtering,
- legend customization,
- time-proportional marker placement,
- fill-price vertical placement,
- export,
- dynamic aggregation,
- persistence,
- live/testnet integration.

### REJECT

Şunları gerekçesiz şekilde kabul etme:

- marker’ı gerçek borsa işlemi gibi göstermek,
- marker ile al/sat tavsiyesi veya gelecek yönü ima etmek,
- OHLC içi kesin işlem sırası çıkarmak,
- fill time’ı bar içinde kesin konumlandırmak,
- client-side finansal hesap yapmak,
- client-side action/bar sorting,
- invalid marker’ı başka bara kaydırmak,
- 409 scope sonrası client slicing,
- ambiguity öncesi kısmi görünümü varsayılan yapmak,
- fake exit veya forced close marker,
- marker yoğunluğunu aggregation ile sessizce azaltmak,
- raw HTML injection,
- external CDN/telemetry/network,
- gereksiz büyük chart dependency,
- marker için yeni persistence/run identity uydurmak.

P1.05.c.3 için küçük, deterministic, read-only, fail-closed ve erişilebilir bir dikey dilim öner. Marker grafik üzerindeki yardımcı bir açıklama olmalı; backend/domain ekonomik doğruluğunu yeniden üretmemelidir.
