# P1.07.d.3 — Fixed-Limit Policy’nin DCA Strategy State’e Bağlanması

## Araştırma amacı

Bu belge, anonim bir yerel Python 3.13 tarihsel OHLCV simülatöründe d.1 application seviyesinde doğrulanmış strict fixed-limit policy’nin mevcut long-only DCA strategy state-machine’ine bağlanıp bağlanamayacağını araştırmak için hazırlanmıştır.

Bu araştırma public API tasarımı değildir. Önce limit policy’nin DCA içindeki hangi ekonomik role ait olacağı, order lifecycle ile position lifecycle’ın nasıl ayrılacağı ve mevcut reserve/risk/anchor kurallarının nasıl korunacağı kanıtlanmalıdır. Public profile, HTTP response, persistence, UI ve marker ancak bu bağlama kanıtlandıktan sonra ayrı kapılarda incelenebilir.

Araştırmacı bu belgeyi proje talimatı değil, kapsam ve soru sözleşmesi olarak kullanmalıdır. Proje adı, yerel klasör, gerçek kullanıcı adı, hesap bilgisi, credential, API anahtarı, özel dataset veya gizli config rapora yazılmamalıdır.

## Doğrulanmış baseline

### D.1 application policy

- Model/policy: explicit historical fixed-limit / strict penetration.
- Immutable order identity: order id, side, exact limit price, original quantity ve placement bar/time.
- Placement barı eligible değildir; yalnız sonraki canonical barlar değerlendirilir.
- BUY strict penetration: low < limit.
- SELL strict penetration: high > limit.
- Equality touch: low == limit veya high == limit; yalnız observation, fill commit yok.
- Strict fill price: exact declared limit price; advantageous open improvement yok.
- Bar başına en fazla bir fixed slice.
- Exact filled/leaves/original quantity conservation.
- Dataset sonu: leaves varsa OPEN_AT_END; sentetik cancel, expiry, exit veya fill yok.
- Same-bar ordering etkileniyorsa application sonucu INDETERMINATE / AMBIGUOUS_OHLC_PATH olur ve o barda yeni fill action commit edilmez.
- Numeric kararlar exact decimal string → Fraction sınırında yürür; binary float, yeni fee/slippage veya uydurma tick/step kuralı yoktur.
- D.1 henüz DCA state, public API veya persistence’e bağlı değildir.

### Mevcut DCA/core baseline

- Core order state, INTENT ile order oluşturur; FILL ekonomik pozisyon/muhasebe etkisi üretir; ORDER_FINAL coverage/lifecycle gözlemi verir.
- Order role’leri BASE, SAFETY:n ve EXIT/STOP ayrımına sahiptir.
- BASE anchor oluşturur; safety plan anchor ve dolum/coverage durumuna bağlıdır.
- Safety order’ın sıradaki seviyesi, pozisyon ve risk bloklarıyla doğrulanır.
- Max entry notional, equity/initial-margin estimate, min quantity/notional ve tick/quantity grid kontrolleri core policy’nin parçasıdır.
- Partial fill sonrası leaves ve coverage tamamlanmamışsa yeni risk açılması güvenli biçimde sınırlanır.
- Late fill, unknown coverage veya açık risk blokları sessizce temiz state sayılmaz.
- Mevcut legacy historical model ayrı bir OHLC simülasyon davranışıdır.
- D.1 fixed-limit tek order davranışı bu DCA kurallarının yerine geçmez ve gerçek exchange execution değildir.

Bu listede bulunmayan mevcut ayrıntılar varsayılmamalıdır. Bilinmeyenler UNKNOWN olarak işaretlenmelidir.

## Dar araştırma sorusu

Yalnızca şu kararı araştır:

> Strict fixed-limit synthetic fill policy, mevcut DCA strategy’de önce hangi role ve hangi event sırasıyla bağlanabilir; bu bağlantı order state, position state, anchor, reserve/risk ve exact muhasebe invariants’ını bozmadan nasıl tanımlanır?

Tüm DCA’yı bir anda limit modele çevirme. En küçük aday dikey dilimi tek bir role ve tek bir lifecycle ile sınırlandır veya DEFER kararı ver.

## Araştırma soruları

### 1. Hangi DCA role ilk adaydır?

BASE, SAFETY:n ve EXIT için ayrı ayrı değerlendir:

- Order ne zaman oluşturuluyor?
- Limit price nereden geliyor?
- İlk eligible bar hangisi?
- Fill olmadan position state nasıl kalıyor?
- Fill olmadan anchor veya safety plan oluşabilir mi?
- Partial fill sonrası role complete sayılır mı?
- EXIT pending iken position/risk state nasıl korunur?

Her rol için ilk aday olup olmadığını, gerekli state’i, riskini ve ACCEPT/SIMPLIFY/DEFER/REJECT kararını yaz. “Tüm roller” ilk mikro dilim olarak kabul edilmemelidir.

### 2. Event ve state ayrımı

Şu kavramları ayrı tanımla:

1. Strategy INTENT: DCA rolünün order oluşturma kararı.
2. ORDER_ACTIVE: placement sonrası pending order.
3. TRIGGER_OBSERVED: strict penetration/equality/no-touch OHLC gözlemi.
4. FILL_COMMITTED: synthetic fixed slice’ın core FILL event’ine çevrilmesi.

Araştır:

- Equality observation core’a FILL göndermeden nasıl taşınır?
- Strict penetration hangi guard’lardan sonra core FILL olabilir?
- Pending order mevcut State.unsettled ile uyumlu mu?
- Aynı pending order için bar başına tek fill nasıl garanti edilir?
- Application result ile core order status tek source of truth olarak nasıl kalır?
- Observation’ın core economic event gibi yayınlanması nasıl engellenir?

### 3. Placement ve look-ahead

- DCA kararının barın hangi zamanında oluştuğu kanıtlanabilir mi?
- Bar close sonrası oluşan order aynı barın high/low alanını görebilir mi?
- İlk eligible bar index/time kimliği nasıl saklanır?
- Placement ve fill aynı timestamp’teyse event sequence nasıl belirlenir?
- Bilgi yoksa ACTIVE_NEXT_BAR zorunlu policy olmalı mı?

### 4. BASE ve anchor

BASE limit fill olmadan:

- position.qty ve anchor null/sıfır mı kalmalı?
- safety plan ve target hesaplanabilir mi?
- max entry notional/equity kontrolü intent’te mi, fill’de mi yapılmalı?
- partial BASE fill sonrası anchor weighted average ile ne zaman oluşmalı?
- BASE EOF’de leaves taşıyorsa strategy state nasıl adlandırılmalı?
- synthetic cancel veya forced close üretmeden bu state nasıl korunmalı?

Anchor timing’i dış kaynakla kanıtlanamıyorsa açık product policy olarak etiketle; piyasa gerçeği gibi sunma.

### 5. SAFETY ladder

SAFETY:n için:

- Safety intent hangi bar kararında oluşur?
- Equality touch safety trigger’ı mı, yalnız observation mı?
- Strict penetration fill olmadan sonraki safety order açılabilir mi?
- Partial safety fill sonrası next safety role ne zaman erişilebilir?
- safety_stopped, blockers, coverage_complete ve leaves ilişkisi nasıl korunur?
- Pending safety varken take-profit değerlendirilir mi?
- Same-bar safety ve take-profit sıra bilgisi yoksa ne zaman INDETERMINATE olur?

### 6. EXIT ve position lifecycle

EXIT için:

- Open position olmadan EXIT intent reddedilmeli mi?
- EXIT quantity position qty mi, fixed slice mı?
- Partial exit realized/average/cost state’ini nasıl etkiler?
- EXIT pending iken yeni safety order açılabilir mi?
- EOF’de pending EXIT ile OPEN_AT_END position status ayrımı nedir?

Çözülmeyen exit/cancel sorularını bu faza zorla dahil etme; ayrı kapı olarak yaz.

### 7. Reserve, risk ve economic posting

Mevcut core davranışını kanıtla:

- Pending limit order için reserve var mı?
- Reserve intent’te mi, fill’de mi hesaplanıyor?
- Partial fill’de reserve kalan miktara göre azalıyor mu?
- Equality observation reserve tüketir mi?
- OPEN_AT_END pending order için reserve nasıl raporlanır?
- Duplicate veya late fill economic posting’i nasıl engellenir?
- filled + leaves = original dışında hangi invariants zorunludur?
- Mevcut fee/slippage pipeline’ına nasıl delegasyon yapılır?
- D.1 generic result’ın henüz position/realized/equity summary üretmemesi binding için bloklayıcı mıdır?

Kanıt yoksa reserve modelini uygulama.

### 8. OHLC ambiguity ve authority

- DCA state’te aynı bar içinde birden fazla ekonomik event mümkün mü?
- Limit strict penetration başka DCA event’iyle birleşince ordering nasıl saptanır?
- Ambiguous bar’da FILL veya ORDER_FINAL üretilmemeli mi?
- INDETERMINATE durumunda final summary, action prefix ve normal execution authority ne olmalı?
- OPEN_AT_END ile INDETERMINATE nasıl ayrılmalı?

Önceki boundary-only marker kararına yeni execution authority ekleme.

### 9. Model/config versioning

- DCA binding yeni model/version mı olmalı?
- Mevcut non-limit fixed davranış limit policy ile yeniden adlandırılmalı mı?
- Fixed slice ve fixed limit policy ayrı mı tutulmalı?
- Role, placement, equality, price, ambiguity ve liquidity policy’leri config hash’e nasıl dahil edilmeli?
- Client arbitrary limit/config gönderebilir mi, yoksa explicit server fixture mı kullanılmalı?

## Zorunlu test ve doğrulama sırası

1. D.1 policy ile mevcut DCA/core state/event davranışlarını ayrı ayrı listele.
2. Mevcut reducer/application için iddia envanteri çıkar.
3. İlk RED testlerini yaz:
   - placement barında look-ahead fill;
   - equality’nin FILL’e dönüşmesi;
   - strict fill öncesi safety/exit açılması;
   - pending order varken ikinci order;
   - partial coverage tamamlanmadan anchor/next risk;
   - duplicate/late fill;
   - ambiguous bar’da optimistic event;
   - EOF’de synthetic cancel/exit;
   - quantity/reserve conservation;
   - legacy davranış değişimi.
4. En küçük GREEN state/event contract öner.
5. Production helper’dan bağımsız küçük state/event reference oracle öner.
6. Exact accounting, determinism ve property/invariant testleri öner.
7. Core reducer testleri ile historical integration testlerini ayır.
8. Public API/profile/UI/persistence kapsam dışı sınırını koru.

- [ ] Tek role ait lifecycle seçildi.

- [ ] Placement barı ve sonraki eligible bar ayrımı test edildi.
- [ ] Equality observation fill değildir.
- [ ] Strict penetration synthetic fill olarak etiketlidir.
- [ ] Core FILL yalnız gerekli reducer guard’larıyla üretilir.
- [ ] Partial fill, leaves, coverage ve anchor ilişkisi exact’tır.
- [ ] Pending order varken yeni risk açma kuralı açıktır.
- [ ] Same-bar ambiguity fail-closed’dur.
- [ ] EOF’de synthetic cancel/exit/fill yoktur.

- [ ] Bağımsız oracle ile sonuç eşleşir.

## Nihai güvenlik şartı

Amaç “limit emri eklemek” değil, DCA state-machine içinde hangi limit olayının ekonomik state değişikliği sayılabileceğini kanıtlamaktır. Role, placement, coverage, anchor, reserve, ambiguity veya EOF semantiği kapanmıyorsa karar DEFER olmalı ve production kodu yazılmamalıdır.
