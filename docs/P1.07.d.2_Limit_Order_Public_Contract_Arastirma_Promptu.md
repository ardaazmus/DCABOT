# P1.07.d.2 — Explicit Fixed-Limit Public Contract ve Profile Entegrasyonu

## Araştırma amacı

Bu belge, anonim bir yerel Python 3.13 tarihsel OHLCV simülatöründe, d.1 application katmanında doğrulanmış sınırlı fixed-limit policy’nin public run-plan ve HTTP response sözleşmesine açılıp açılmayacağını araştırmak için hazırlanmıştır.

Araştırmacı bu belgeyi proje talimatı değil, kapsam ve soru sözleşmesi olarak kullanmalıdır. Proje adı, yerel klasör, gerçek kullanıcı adı, özel dataset yolu, hesap bilgisi, credential, API anahtarı veya gizli config rapora yazılmamalıdır.

## Önceki doğrulanmış baseline

Aşağıdaki davranış d.1 application mikro diliminde test edilmiştir:

- Model/policy: explicit 'historical_ohlcv_partial_fixed_limit_v1' / 'FIXED_LIMIT_STRICT_V1'.
- 'FixedLimitOrder' immutable order id, side, exact limit price, original quantity ve placement bar/time identity taşır.
- Placement barı eligible değildir; yalnız sonraki canonical barlar gözlemlenir.
- BUY için 'low < limit_price', SELL için 'high > limit_price' strict penetration synthetic fill observation üretir.
- 'low == limit_price' veya 'high == limit_price' yalnız 'EQUALITY_TOUCH' observation’dır; fill commit edilmez.
- Strict penetration’da fill price exact declared 'limit_price'’tır; advantageous open price improvement uygulanmaz.
- Her eligible barda en fazla bir fixed slice fill edilir; exact remainder ve quantity conservation korunur.
- Dataset sonunda leaves varsa 'OPEN_AT_END'; sentetik cancel, expiry, exit veya fill üretilmez.
- Same-bar ordering etkileniyorsa application sonucu 'INDETERMINATE / AMBIGUOUS_OHLC_PATH' olur ve o barda yeni fill action commit edilmez.
- Numeric kararlar exact decimal string → 'Fraction' sınırında yürür; binary float, yeni fee/slippage veya uydurma tick/step kuralı yoktur.
- d.1 public profile, HTTP endpoint, persistence, UI ve marker authority’ye bağlanmamıştır.

Bu baseline dışındaki mevcut uygulama ayrıntıları araştırmacı tarafından varsayılmamalıdır. Bilinmeyenler 'UNKNOWN' olarak bırakılmalıdır.

## Bu araştırmanın dar kapsamı

Yalnızca şu soruya cevap ver:

> D.1’deki explicit fixed-limit application sonucunu, legacy historical API’yi bozmadan ve sentetik fill’i gerçek exchange execution gibi göstermeden, hangi en küçük public profile/run-plan/response contract’ı ile erişilebilir yapmak güvenlidir?

Kapsam dışı:

- Stop ve stop-limit.
- Cancel/fill race.
- Latency.
- Queue priority.
- Order book/depth replay.
- Market volume participation.
- Gerçek exchange bağlantısı veya emir gönderimi.
- Persistence/save/reopen/compare.
- UI, grafik, marker, tooltip veya mobil görsel karar.
- Yeni fee/slippage modeli.
- Yeni ROI, equity, drawdown, Sharpe/Sortino veya benchmark metriği.
- D.1’de kararı verilmemiş equality fill ve open price improvement.

## Karar formatı

Araştırma sonunda tek bir karar ver:

- 'ACCEPT': D.1 policy’si için en küçük public contract kanıtlandı.
- 'SIMPLIFY': Yalnız domain/application + run-plan veya yalnız HTTP response gibi daha dar bir yüzey güvenli.
- 'DEFER': Public boundary’de anlam, uyumluluk veya authority riski kapanmadı.
- 'REJECT': Bu policy public olarak açılırsa yanlış kesinlik/yanlış execution yorumu kabul edilemez.

'ACCEPT' veya 'SIMPLIFY' seçilirse production kodu yazma; yalnız alan sözleşmesi, invariant, hata davranışı ve test planı öner.

## Ana araştırma soruları

### 1. Profile ve model kimliği

- D.1 behavior yeni bir explicit historical profile olarak mı açılmalı, yoksa mevcut fixed profile’a ayrı bir capability mi eklenmeli?
- Legacy 'historical_ohlcv_v1' kesin olarak değişmeden kalabilir mi?
- Mevcut 'historical_ohlcv_partial_fixed_v1' limit olmayan fixed-slice davranışını koruyarak limit modelinden ayrı tutulmalı mı?
- Önerilen model/profile kimliği versioned, allowlisted ve deterministic olmalı mı?
- Profile listesi public olduğunda kullanıcıya 'synthetic OHLC policy' ve 'real exchange replay değil' provenance’ı nasıl taşınmalı?
- Mevcut profile adlarına yeni anlam yüklemek migration riski doğurur mu?

### 2. Run-plan binding

- Dataset symbol/interval/period/artifact revision ile limit profile’ın bağlanması için hangi alanlar zorunludur?
- 'placement_bar_index' ve 'placement_open_time_us' client’tan alınmalı mı, yoksa yalnız server/application tarafından mı üretilmeli?
- Serbest client order tanımı public API’ye açılacaksa hangi alanlar allowlist olmalı?
- 'side', 'limit_price', 'original_qty', 'slice_qty' exact string contract’ı nasıl doğrulanmalı?
- Placement identity dataset’e ait değilse veya timestamp eşleşmiyorsa 4xx mi, domain 'INDETERMINATE' mi dönmelidir?
- Generic tek-limit order denemesi, gerçek DCA strategy state’ine bağlanmadan public profile olarak sunulabilir mi?
- Public request arbitrary strategy/order payload kabul etmeden explicit fixed fixture ile sınırlanmalı mı?

### 3. Response’ta observation ve fill ayrımı

Response aşağıdaki anlamları karıştırmamalıdır:

- order active,
- trigger/price observation,
- synthetic fill committed,
- final order status.

Şunları değerlendir:

- 'observations' ve 'actions' ayrı alanlar olmalı mı?
- 'EQUALITY_TOUCH' response’ta normal action gibi görünmeden nasıl adlandırılmalı?
- 'fill_committed=false' bir observation’da economic summary veya execution marker yetkisi doğurur mu?
- 'OPEN_AT_END', 'FILLED' ve 'INDETERMINATE' status’ları aynı response union’ında nasıl ayrılmalı?
- Exact 'filled_qty', 'leaves_qty', 'original_qty', event sequence, bar index ve 'open_time_us' alanlarından hangileri public için zorunludur?
- 'fill_price' yalnız committed action’da non-null olmalı mı?
- No-touch barları public response’ta bounded observation olarak döndürmek gerekir mi, yoksa yalnız son durum yeterli mi?
- Response boundedness için action/observation count üst sınırı ve serialized byte sınırı nedir?

### 4. Authority ve yanlış yorum riski

- D.1 synthetic fill action’ı 'FULL_RUN' veya 'TRADE_EXECUTION' authority taşıyabilir mi?
- Model gerçek order-book replay olmadığı için provenance enum’ı nasıl adlandırılmalı?
- 'strict penetration' gözlemi ile fill commit’i public’te ayrı gösterilebilir mi?
- 'EQUALITY_TOUCH' için 'marker_authority=NONE' korunmalı mı?
- 'INDETERMINATE' için action prefix veya partial economic state public’te açılmalı mı? Önceki boundary-only kararlarını dikkate al ve yeni authority icat etme.
- 'OPEN_AT_END' gerçek exchange open order state’i olarak değil dataset boundary state’i olarak nasıl açıklanmalı?
- Normal trade marker veya grafik bu fazda kesinlikle dışarıda kalmalı mı?

### 5. Exact numeric ve schema sınırı

- Public JSON’da decimal quantity/price/fill/fee alanlarının string kalması zorunlu mudur?
- Pydantic/FastAPI serialization sırasında float coercion nasıl engellenir?
- Tick/quantity step config’te mevcut olsa bile public request bunları değiştirebilir mi?
- 'Decimal', 'Fraction', quantization ve fee değerlerinin API boundary’de hangi kısmı görünmelidir?
- Client’ın number göndermesi 422 Problem Details ile reddedilmeli mi?
- 'NaN', 'Infinity', exponent veya locale decimal string’leri nasıl reddedilmelidir?
- Public config hash hangi policy/model/capability alanlarını kapsamalıdır?

### 6. HTTP error ve compatibility

- Bilinmeyen model/profile için mevcut error convention’a uygun hangi 4xx kodu ve problem code kullanılmalı?
- Legacy model ile limit-only alanların birlikte gönderilmesi sessizce yok sayılmalı mı, yoksa explicit unsupported-model hatası ile reddedilmeli mi?
- Stale dataset/artifact/config revision ile limit profile isteği nasıl fail-closed olmalı?
- Invalid placement bar, wrong open time, off-grid quantity/price, zero/negative value ve over-quantity için ayrı hata sınıfları gerekli mi?
- Same-bar ambiguity normal HTTP hata mı, yoksa güvenli domain result mı?
- Yeni response union alanları legacy client’ın eski JSON parse’ını bozabilir mi?
- Optional field eklemek mi, ayrı model response union’ı mı daha güvenlidir?
- OpenAPI/schema generation ve gerçek ASGI serialization birlikte test edilmeden public contract kapanabilir mi?

### 7. Execution mode ve data provenance

- Public response açıkça 'OFFLINE', 'HISTORICAL', 'SIMULATED', 'SYNTHETIC_OHLCV_FILL' benzeri bounded provenance taşımalı mı?
- Dataset metadata’sında source/artifact hash var; public response path/URL/credential göstermeden hangi revision alanlarını taşımalı?
- Kullanıcı bir synthetic fill’i gerçek exchange execution’ı sanmaması için hangi zorunlu metin/machine field gerekir?
- D.1 modelinin venue-specific olmadığı nasıl gösterilir?
- Model/version/policy/equality/price/liquidity/ambiguity policy alanlarından hangileri immutable provenance olmalı?

## Aday public tasarımlar

### A. Yeni explicit profile + ayrı response union

Limit policy için ayrı profile/model ve ayrı strict response tipi. Legacy ve mevcut non-limit fixed profile değişmez.

Araştır:

- en küçük zorunlu alanlar,
- profile registry migration,
- frontend’in profile listesine etkisi,
- response union compatibility,
- public risk.

### B. Mevcut fixed profile içinde explicit execution capability

'execution_policy' veya eşdeğer allowlisted capability ile limit davranışı açılır. Default eski fixed behavior’dır.

Araştır:

- capability’nin sessizce default’a dönüşme riski,
- config hash kapsamı,
- legacy guard,
- response provenance ve backward compatibility.

### C. Public endpoint yok; yalnız server-side test/demo fixture

D.1 application policy testlerle korunur, public catalog/run-plan/API’ye açılmaz.

Araştır:

- ürün açısından bunun yeterli olup olmadığı,
- public açmanın hangi kanıtlar olmadan erken olduğu,
- sonraki d.2’den sonra gerekebilecek ayrı API ve UI kapıları.

## Zorunlu response taslağı değerlendirmesi

Aşağıdaki taslağı kabul etmek zorunda değilsin; alanların gerekli, gereksiz veya riskli olduğunu kanıtla:

~~~text
execution_status:
  COMPLETED
  OPEN_AT_END
  INDETERMINATE

model:
  historical_ohlcv_partial_fixed_limit_v1

policy:
  FIXED_LIMIT_STRICT_V1

provenance:
  execution_kind: SYNTHETIC_OHLCV_FILL
  venue_replay: false
  placement_policy: ACTIVE_NEXT_BAR
  equality_policy: OBSERVE_ONLY
  price_policy: LIMIT_PRICE_ONLY
  liquidity_policy: FIXED_SLICE_NO_MARKET_VOLUME
  ambiguity_policy: FAIL_CLOSED

order:
  order_id: opaque string
  side: BUY | SELL
  limit_price: decimal string
  original_qty: decimal string
  placement_bar_index: integer
  placement_open_time_us: integer

observations:
  - bar_index
    open_time_us
    kind: NONE | EQUALITY_TOUCH | STRICT_PENETRATION
    trigger_observed: boolean
    fill_committed: boolean

actions:
  - event_sequence
    bar_index
    open_time_us
    observation_kind: STRICT_PENETRATION
    fill_price: decimal string
    quantity: decimal string
    cumulative_filled_qty: decimal string
    leaves_qty: decimal string

summary:
  original_qty: decimal string
  filled_qty: decimal string
  leaves_qty: decimal string
  status: PENDING | PENDING_TOUCH_ONLY | PARTIALLY_FILLED | FILLED | OPEN_AT_END | INDETERMINATE
~~~

Özellikle şu riskleri kontrol et:

- 'execution_status' ile order 'status' aynı kavram değilse isimleri ayır.
- 'actions' dolum action’ıdır; observation’ı action gibi gösterme.
- 'OPEN_AT_END' completed economic summary anlamına gelmemeli.
- 'INDETERMINATE' durumda hangi alanların null/boş olması gerektiğini belirle.
- Public 'summary' içinde fee/slippage yoksa bunlar uydurulmamalı.
- Normal marker authority ancak gerçekten committed fill ve full-run kanıtı varsa açılmalı.

## Zorunlu doğrulama sırası

Rapor şu sırayı takip etmeli; yalnız öneri vermek yeterli değildir:

1. Mevcut legacy ve non-limit fixed public contract’ın beklenen davranışını açıkça listele.
2. D.1 application policy’nin hangi alanlarını public’e taşımadan önce tekrar doğrulamak gerektiğini belirt.
3. İlk RED test setini yaz:
   - model/profile implicit açılması,
   - legacy response değişmesi,
   - observation’ın action gibi görünmesi,
   - equality’nin fill yapılması,
   - open price improvement sızması,
   - float JSON coercion,
   - placement same-bar look-ahead,
   - ambiguous fill publication.
4. En küçük GREEN public contract ve onun zorunlu guard’larını öner.
5. Production kodu ile aynı helper’ı çağırmayan bağımsız JSON/reference kontrolü öner.
6. Gerçek ASGI request/response serialization, OpenAPI/schema ve body-size sınırı testlerini belirt.
7. Legacy full regression ve deterministic repeated request testlerini belirt.
8. Testler ile kaynak/semantik uyuşmuyorsa implementation kararını 'DEFER' yap.

## Kabul kriterleri

Öneri 'ACCEPT' veya 'SIMPLIFY' olacaksa en az şu kriterler cevaplanmalıdır:

- [ ] Default legacy davranış değişmiyor.
- [ ] Limit policy yalnız explicit model/profile/capability ile açılıyor.
- [ ] Public model id ve policy version allowlisted.
- [ ] Placement barı ve sonraki eligible bar ayrımı response/test ile sabit.
- [ ] 'EQUALITY_TOUCH' fill action değil.
- [ ] Strict penetration synthetic fill olarak etiketli.
- [ ] Fill price exact limit string; open improvement yok.
- [ ] Fixed slice, remainder ve quantity conservation public invariant.
- [ ] Same-bar ambiguity fail-closed.
- [ ] EOF 'OPEN_AT_END'; synthetic cancel/exit/fill yok.
- [ ] 'INDETERMINATE' normal execution authority vermiyor.
- [ ] Decimal alanlarda float coercion yok.
- [ ] Path, URL, credential ve arbitrary config response’a sızmıyor.
- [ ] Error contract explicit ve stale revision guard’lı.
- [ ] ASGI serialization gerçek request ile doğrulanıyor.
- [ ] Bağımsız reference oracle ile response eşleşiyor.
- [ ] Persistence ve UI bu faza girmiyor.
